## Welcome

### What is Kubernetes?

Kubernetes (K8s) is an open-source platform for **automating the deployment, scaling and management**
of container applications. Originally developed by Google, the Cloud Native Computing Foundation
(CNCF) maintains it today.

### Why Kubernetes?

Kubernetes runs containerised applications reliably, automatically and at scale. Instead of starting
every container manually on a server and intervening yourself when something fails, Kubernetes takes
over the whole orchestration: it distributes containers intelligently across the available machines,
restarts failed containers automatically, scales applications up or down as needed and enables
updates without downtime. Kubernetes shows its strength especially in microservice architectures
with many services that influence each other -- it decouples teams from the underlying
infrastructure and creates a uniform, repeatable operating standard, whether on-premises, in the
cloud or in a hybrid setup.

### When not to use Kubernetes?

<Image src={knba10010} alt="Why not Kubernetes * Created with Microsoft Copilot" />

Kubernetes is not always the right choice. For simple web applications, monolithic systems or small
projects with only one or a few containers the operational effort is often disproportionate -- a
single server with Docker Compose or a platform as a service (PaaS) such as Heroku, Fly.io or
Railway gets you there faster and with less complexity. Without a team that holds DevOps know-how,
Kubernetes can also quickly become a maintenance trap: the learning curve is steep, and daily
administration (updates, troubleshooting, networking, storage) requires specialised knowledge.
Kubernetes suits stateful workloads with high I/O requirements (e.g. large databases) just as
little, because a classic bare-metal server or a managed database offers better performance and
simpler handling. Rule of thumb: from about 5-10 (micro)services on, or when automation, scaling and
resilience are explicit requirements, Kubernetes pays off.

### What for?

- **[Container orchestration](/docs/kubernetes-basis-en/90-glossary#container-orchestration)** -- Managing hundreds of containers across several servers
- **[Self-healing](/docs/kubernetes-basis-en/90-glossary#self-healing)** -- Automatic restart of failed containers
- **[Scaling](/docs/kubernetes-basis-en/90-glossary#scaling)** -- Scaling up and down by command or automatically
- **[Rolling updates](/docs/kubernetes-basis-en/90-glossary#rolling-updates)** -- Updating applications without downtime
- **[Service discovery](/docs/kubernetes-basis-en/90-glossary#service-discovery)** -- Automatic name resolution between applications

## Core concepts

### Analogy

To make Kubernetes concepts easier to grasp we use an **analogy to a logistics centre**. Just as a
logistics centre manages parcels -- it decides where they are stored, how they are transported, and
makes sure automatically that everything arrives in the right place -- Kubernetes takes over these
tasks for container applications.

Relating to the DevOps workflow above: the developer builds the parcel (`docker build`), puts it into
storage (registry), and the logistics centre (Kubernetes) takes over delivery from there to the
recipient (production) -- reliably, automatically and with self-healing when problems occur.

| Kubernetes concept | Analogy                  | Description                                                                    |
| ------------------ | ------------------------ | ------------------------------------------------------------------------------ |
| [**Cluster**](/docs/kubernetes-basis-en/90-glossary#cluster)        | Entire logistics centre  | All machines and resources that work together                                  |
| [**Control Plane**](/docs/kubernetes-basis-en/90-glossary#control-plane)  | Office / headquarters    | Makes all decisions: what runs where, what happens on problems                 |
| [**Worker Node**](/docs/kubernetes-basis-en/90-glossary#worker-node)    | Workstation / truck      | The machine on which containers actually run                                   |
| [**Pod**](/docs/kubernetes-basis-en/90-glossary#pod)            | Parcel / delivery unit   | Smallest deployable unit, holds one or more containers                         |
| [**Deployment**](/docs/kubernetes-basis-en/90-glossary#deployment)     | Work instruction         | Describes the desired state ("2 Chromium instances should run")                |
| [**Service**](/docs/kubernetes-basis-en/90-glossary#service)        | Phone number             | Stable address through which an application stays reachable                    |
| [**Namespace**](/docs/kubernetes-basis-en/90-glossary#namespace)      | Department               | Logical separation inside a cluster                                            |

### Cluster architecture

<Image src={knba10020} alt="Kubernetes architecture * Created with Microsoft Copilot" />

A Kubernetes cluster consists of two areas: the **Control Plane**, which steers the entire cluster,
and the **Worker Nodes**, on which the applications actually run. All components communicate with
each other exclusively through the API server.

### Control Plane

The Control Plane is the brain of the cluster. It watches the state of all resources and makes sure
the desired state always matches the actual state.

| Component                   | Function                                                     |
| --------------------------- | ------------------------------------------------------------ |
| [**kube-apiserver**](/docs/kubernetes-basis-en/90-glossary#kube-apiserver)          | Central entry point. Every kubectl command goes here. |
| [**etcd**](/docs/kubernetes-basis-en/90-glossary#etcd)                    | Key-value database. Stores the entire cluster state. |
| [**kube-scheduler**](/docs/kubernetes-basis-en/90-glossary#kube-scheduler)          | Decides on which node a new Pod should run.     |
| [**kube-controller-manager**](/docs/kubernetes-basis-en/90-glossary#kube-controller-manager) | Continuously reconciles actual state with desired state. |
| [**CoreDNS**](/docs/kubernetes-basis-en/90-glossary#coredns)              | DNS service for service discovery. Translates service names into ClusterIPs, reading from etcd at the moment. |

### Worker Nodes

Worker Nodes are the machines on which the actual workloads run. Every node holds three core
components that work closely with the Control Plane.

| Component             | Function                                                          |
| --------------------- | ----------------------------------------------------------------- |
| [**kubelet**](/docs/kubernetes-basis-en/90-glossary#kubelet)           | Agent on every node. Makes sure containers run inside Pods. |
| [**kube-proxy**](/docs/kubernetes-basis-en/90-glossary#kube-proxy)        | Network proxy. Manages network rules for Services.            |
| [**Container Runtime**](/docs/kubernetes-basis-en/90-glossary#container-runtime) | Runs containers (e.g. containerd, CRI-O).                     |

### Optional: add-ons & extensions

Further optional components extend Kubernetes, but they do not always have to be installed:

- **Ingress Controller** — Manages routing to Services (a more elegant alternative to NodePort)
- **Metrics Server** — Collects CPU and memory metrics from nodes and Pods (needed for `kubectl top` and autoscaling)
- **Dashboard** — Web UI for managing the cluster

### Analogy: logistics company

To understand the Kubernetes architecture better, consider an analogy to a logistics company that
delivers parcels worldwide:

**Kubernetes cluster = logistics company**
A whole logistics company with all its branches, vehicles and employees corresponds to a Kubernetes
cluster with all its components.

**Control Plane = central management**
The management of a logistics company makes all the important decisions: where do new parcels get
collected? How many deliveries go where? What happens during bottlenecks or failures? In Kubernetes
the Control Plane takes over exactly these planning and steering tasks.

**Worker Nodes = regional warehouses and transport vehicles**
The physical locations where parcels are buffered and from which they are delivered correspond to the
Worker Nodes. Every regional warehouse (node) has its own resources: staff (CPU), storage space
(memory), transport capacity (network) and packing material (container runtime).

**Pods = parcels**
The smallest units of work in Kubernetes are Pods -- they correspond to the parcels in the logistics
company. Every parcel/Pod holds one or more items/components (containers) that belong together and
are transported/run together.

**Deployments = freight orders**
A freight order describes how many copies of a good should be delivered to various places. In the
same way a Deployment defines how many Pods (equivalent "parcels") should be distributed across the
cluster in which configuration. The dispatcher (kube-controller-manager) makes sure the agreed
number of parcels stays on the road at all times.

**Services = hotline numbers**
A service hotline in a logistics company stays reachable no matter which employee answers the call
at the moment. In the same way a Kubernetes Service offers a stable IP address and a port through
which clients always reach the application -- regardless of which Pods currently run on which node.

**Labels = address labels**
Every parcel gets labels with important information: destination, urgency, recipient group. In
Kubernetes, labels are metadata of that kind; they allow organising, selecting and linking resources.
A Service uses labels to know which Pods belong to it -- like a hotline that calls the right
colleague based on the department code.

**Ingress Controller = reception and central telephone system**
A company's reception takes external calls and forwards them to the right internal extension. An
Ingress Controller does the same for web requests: it receives external traffic and forwards it to
the matching Services in the cluster according to defined rules.

### Kubernetes components in the logistics company

**kube-apiserver = headquarters / central office**
The kube-apiserver is the main building of the logistics company, where all requests arrive and from
where all instructions go out. Every employee (driver, warehouse worker or manager) has to check in
here before doing anything. All communication runs through this central hub.

**etcd = archive / main database**
etcd is the huge archive of the company, where all important information is stored: who received
which parcels? Which routes are available? Who is on holiday right now? This database matters so
much that it is backed up several times - comparable to several identical archives at different
locations.

**kube-scheduler = traffic control centre / dispatch**
kube-scheduler acts like the dispatch desk in a logistics company. When new parcels arrive, it
decides which truck (node) can transport the parcel best, based on factors such as load, distance and
special requirements.

**kube-controller-manager = quality management / process supervisor**
kube-controller-manager is like quality management, which continuously checks whether everything goes
to plan. When a parcel does not arrive on time or a truck breaks down, it steps in and restores the
original state - for example by sending out a new truck.

**CoreDNS = telephone exchange / address book**
CoreDNS is like the central telephone exchange with a huge address book. When an employee wants to
contact another department, they call the exchange and get the current extension - no matter whether
the colleagues sit in the office or are on the road.

**kubelet = regional manager / site manager**
Every node runs a kubelet that works like a regional manager. It receives instructions from the
headquarters and makes sure everything runs properly in its regional warehouse (node): parcels are
accepted, employees work and trucks leave.

**kube-proxy = security staff / access control**
kube-proxy is the security staff of every regional warehouse. It controls who may enter the warehouse
and makes sure parcels are only forwarded to authorised people. It also keeps track of which parcels
are where in the warehouse.

**Container Runtime = packing department / cargo area**
The container runtime is the packing department that takes care of correct packing and loading of the
parcels. It makes sure every parcel (container) is stowed safely and nothing gets damaged during
transport.

### Namespaces

Namespaces are logical separations inside a cluster. They allow isolating resources of different
teams, projects or environments (e.g. `dev`, `staging`, `prod`) from each other without running
separate clusters. You can assign permissions and resource limits per Namespace.

```bash
# List existing Namespaces.
kubectl get namespaces
```

Default Namespaces:

| Namespace         | Purpose                                                  |
| ----------------- | -------------------------------------------------------- |
| `default`         | Default Namespace for objects without explicit assignment |
| `kube-system`     | Kubernetes system components                             |
| `kube-public`     | Publicly readable data (e.g. cluster info)               |
| `kube-node-lease` | Node heartbeat data                                      |

### Imperative vs. declarative

Kubernetes offers two ways to create resources:

- **Imperative**--You give concrete commands that run immediately.
  Example: `kubectl create namespace k8s-training`
  Ideal for quick tests and experiments.

- **Declarative**--You define the desired state in a YAML file
  and let Kubernetes establish that state.
  Example: `kubectl apply -f create-namespace.yaml`
  The standard in practice, because manifests can be versioned, shared and
  reviewed.
<br/>
On this day you see both approaches side by side--starting with the
imperative path for a quick entry.

## Deploying Chromium

In this block we deploy a complete browser (Chromium) in the cluster -- imperatively, so directly via
the command line.

### What is a Deployment?

A **Deployment** is one of the most important resources in Kubernetes. It describes the **desired
state** for an application:

- **How many Pods** should run? (replicas)
- **Which image** should be used?
- **How should the Pods** be configured? (environment variables, ports, volumes)

The Deployment watches the actual state continuously and makes sure it matches the desired state.
When a Pod crashes or gets deleted, the Deployment creates a new one automatically -- that is
**self-healing**.

**Analogy to the logistics centre:**

Picture a Deployment like a **work instruction in the logistics centre**:
*"Two finished parcels (Pods) must always be ready in the warehouse. When one
ships (fails), a new one has to be packed immediately."*

The warehouse manager (Kubernetes Control Plane) watches the number of finished parcels all the time.
When a parcel disappears, they pack a new one right away -- without anyone
intervening manually.

In short: a Deployment is the "work instruction" for Kubernetes that says:
*"I want this application to run exactly like this."*

### Imperative

```bash
kubectl create deployment chromium --image=lscr.io/linuxserver/chromium:latest --replicas=1
```

<br/>

<Notice type="warning">

**Error `admission webhook ... require-resource-requirements ... denied the request`?** Your cluster
enforces that every container declares `resources.requests` and `resources.limits` for CPU and
memory. `kubectl create deployment` offers no direct option for that.

```bash

kubectl -n k8s-training create deployment chromium --image=lscr.io/linuxserver/chromium:latest --replicas=1 --dry-run=client -o json \
| kubectl set resources --local -f - -c chromium --requests=cpu=250m,memory=512Mi --limits=cpu=1,memory=1Gi -o json \
| kubectl -n k8s-training apply -f -

```

Day 2 explains what `resources` means. The YAML examples in this training already contain the
`resources` block so they work on such a cluster as well.

</Notice>

**Overwrite the Deployment (with a new image or replicas):**

When you want to change the Deployment (e.g. a different image or a different number of replicas),
use `kubectl set image` or `kubectl scale`:

```bash
# Upgrade to a different version (e.g. latest → v2.0).
kubectl set image deployment/chromium chromium=lscr.io/linuxserver/chromium:v2.0

# Change the number of replicas.
kubectl scale deployment chromium --replicas=3

```

You can check the changes with `kubectl get pods` after every step. Explain the behaviour in the
team.

**Delete the Deployment:**

```bash
# Delete the Deployment and all its Pods.
kubectl delete deployment chromium
```

> ⚠️ **IMPORTANT:** `kubectl delete deployment` also deletes all Pods managed by this Deployment! The
> data inside the Pods is lost (unless volumes are used).

**Quick access: port forwarding**

Before we build a Service, you can already open Chromium in the browser. `kubectl port-forward`
pulls a container port directly onto your machine -- without a Service, without a NodePort, without a
firewall exception. Create the chromium Deployment again first, then set up port forwarding.

```bash
kubectl port-forward deployment/chromium 4000:3000
```

The command addresses the Deployment and therefore exactly one Pod: `4000` is the port on your
machine, `3000` the port inside the container. Open `http://localhost:4000` and stop the forwarding
later with `Ctrl+C`. No Service is needed for that -- it comes later.

<Notice type="info">
**Example: an SSH container as a "harness"**

Not every application has a web UI. SSH access to the cluster is a classic "harness": start a
bastion in the Namespace, reach it exclusively through `port-forward`, and use it as a shell for
everything running in the cluster.

File `ssh-bastion-deployment.yaml`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ssh-bastion
  namespace: k8s-training
spec:
  replicas: 1
  selector:
    matchLabels:
      app: ssh-bastion
  template:
    metadata:
      labels:
        app: ssh-bastion
    spec:
      containers:
        - name: sshd
          image: lscr.io/linuxserver/openssh-server
          resources:
            requests:
              cpu: "50m"
              memory: "64Mi"
            limits:
              cpu: "200m"
              memory: "128Mi"
          ports:
            - containerPort: 2222
          env:
            - name: PUID
              value: "1000"
            - name: PGID
              value: "1000"
            - name: TZ
              value: "Europe/Berlin"
            - name: USER_NAME
              value: "training"
            - name: PUBLIC_KEY
              value: "ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI... insert your own public key here"
```

File `ssh-bastion-service.yaml`:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: ssh-bastion
  namespace: k8s-training
spec:
  type: ClusterIP          # reachable only inside the cluster
  selector:
    app: ssh-bastion
  ports:
    - port: 22
      targetPort: 2222
```

```bash
kubectl apply -f ssh-bastion-deployment.yaml
kubectl apply -f ssh-bastion-service.yaml
kubectl port-forward svc/ssh-bastion 2222:22 -n k8s-training
```

On the client side, add an entry to `~/.ssh/config`:

```text
Host ssh-bastion
  HostName 127.0.0.1
  Port 2222
  User training
  IdentityFile ~/.ssh/id_ed25519_training
  StrictHostKeyChecking accept-new
  UserKnownHostsFile ~/.ssh/known_hosts_training
```

Afterwards, `ssh ssh-bastion` is all you need. The key is a placeholder for your own **public**
key, never the private one.

Alternatively, you can use an SSH tunnel instead of `kubectl port-forward`:

```bash
ssh -t -o StrictHostKeyChecking=accept-new -o UserKnownHostsFile=c:\Users\<USER>\.ssh\known_hosts -o HostKeyAlias=fd-dev -o ServerAliveInterval=30 -o ServerAliveCountMax=3 -o 'ProxyCommand=kubectl --kubeconfig C:/Users/dakoenig/.kube/MYCLUSTER.yaml --context MYCLUSTER -n fd-infra exec -i fd-dev-container -- nc localhost 2222' -i C:\Users\<USER>\.ssh\mykey.key appuser@localhost
```
</Notice>

### Setting up a Service

Now we make Chromium reachable from the outside. We create a **NodePort Service** imperatively.

**Analogy to the logistics centre:**

Picture the NodePort Service like a **call into the logistics centre**:

1. **External customer** calls the logistics centre (your browser calls `Node-IP:3xxxx`)
2. **External number (NodePort)**--The customer dials the public extension 3xxxx (the automatically assigned NodePort)
3. **Reception at the node**--A worker node answers the call (kube-proxy on that node)
4. **Internal switchboard (Service/ClusterIP:4000)**--The reception forwards the call to the central Service switchboard
5. **Staff assignment (Pod)**--The switchboard picks a free employee (a Pod)
6. **Workplace (targetPort=3000)**--The employee is reached at their workplace (container port 3000)
7. **Response**--The employee's answer travels back through the switchboard and the reception to the customer


<br/>
<Image src={knba10040} alt="Node service communication in the logistics centre * Created with Microsoft Copilot" />

<br/>

> 💡 **Remember:** exactly as in the logistics centre, a **stable extension** (Service) exists that
> stays reachable all the time--no matter which employee (Pod) handles the request right now!

<br/>

```bash
kubectl expose deployment chromium \
  --type=NodePort \
  --name=chromium \
  --port=4000 \
  --target-port=3000
```
<br/>

**Important distinction:**

- **`--port=4000`**: port the Service listens on **inside the cluster** (for Pods internally)
- **`--target-port=3000`**: port the **container** listens on
- **NodePort**: port opened on the **nodes** (external access) -- automatically in the range
  30000-32767
<br/>


**What is the ClusterIP?**

The **ClusterIP** is an **internal, stable IP address** of the Service. It is the central endpoint that
always stays the same -- no matter how often Pods get recreated or their IP addresses change.

**The NodePort forwards to the ClusterIP** -- that is the "actual" Service. The NodePort only is the
**external entry point** for traffic from outside.

```bash
kubectl get service chromium
# Output: chromium   NodePort   10.43.25.123   3000:30123/TCP   ...
#                        ^^^^^^^^^^^ This is the ClusterIP (internal).
#                                   ^^^^^^^ This is the NodePort (external).
```

**Why do you need the ClusterIP?**

- **Stability:** the ClusterIP always stays the same, even when Pods change
- **Internal communication:** other Pods in the cluster reach the Service via the ClusterIP (without NodePort)
- **Abstraction:** the NodePort only is an "entry gate" -- the actual logic lives in the ClusterIP

**Without the ClusterIP** every external client would have to know the Pod IPs directly -- and those
change constantly! The ClusterIP is the **stable intermediary**.

Kubernetes picks a NodePort from the range 30000-32767 automatically. Check the **actual** assigned
port.

<Notice type="info">
  **Maybe you wonder how the Service handles several Pods and does the load balancing?**

  Good question! The answer: **the Service distributes incoming requests automatically in round-robin
  across all Pods that match its label selector** -- completely transparent for the client.

  **How does that work exactly?**

  1. **kube-proxy on every node** watches the API server continuously and thereby learns which Pods
     belong to which Service and which IP addresses they have.
  2. **iptables/IPVS rules** are written by kube-proxy on every node. These rules say: "when a packet
     goes to the ClusterIP:Port of the Service, forward it at random (round-robin) to one of the Pod
     IPs."
  3. **The client notices nothing** -- it only addresses the ClusterIP and gets an answer without
     knowing which Pod actually answered.

  **Example:** your Chromium Service has 3 replicas (`replicas: 3`). Three clients call
  `http://<ClusterIP>:4000` at the same time:

  - Client 1 → Pod A (Chromium #1)
  - Client 2 → Pod B (Chromium #2)
  - Client 3 → Pod C (Chromium #3)
  - Client 4 → Pod A (from the start again)

  **Good to know:**
  - The Service distributes **new connections only** (TCP connections). A connection once
    established stays with the same Pod.
  - When a Pod fails, kube-proxy removes it from the rotation automatically -- new requests go to the
    remaining Pods only.
  - The Service has **no knowledge of the load** on the individual Pods. It simply distributes evenly
    without checking whether a Pod is under heavy load at the moment. That is what the
    **HorizontalPodAutoscaler** is for (comes later).

  **Analogy to the logistics centre:** imagine the service hotline has several employees (Pods), all
  able to take the same call. The telephone system (kube-proxy) accepts the call and forwards it to
  the next free employee -- without the caller knowing who answers. When an employee drops out (Pod
  dies), the system simply stops calling them.
</Notice>

Kubernetes picks a NodePort from the range 30000-32767 automatically. Check the **actual** assigned
port.

## Labels in Kubernetes

<Image src={knba10030} alt="Labels in Kubernetes * Created with Microsoft Copilot" />

### What are labels?

**Labels** are key-value pairs attached to Kubernetes resources (Pods, Deployments, Services, nodes,
…). You define them freely and they carry no fixed meaning for Kubernetes itself -- they only serve
to **identify, group and select** resources.

```yaml
metadata:
  labels:
    app: chromium
    environment: training
    version: "1.0"
    team: devops
```

Labels are **no comments** -- they are machine-readable metadata that Kubernetes actively reacts to.

---

### Why do labels matter so much?

Labels are the **backbone of communication** between Kubernetes resources. Without labels no Service
would know which Pods to address, no Deployment would recognise its own Pods, and no monitoring tool
could group resources in a meaningful way.

Concretely, labels fulfil three central jobs:

#### Selection (label selectors)

The most important use of labels is **selection**: other resources use a *label selector* to choose
the Pods they act on.

| Resource | What does it use labels for? |
|---|---|
| **Service** | Forwards traffic only to Pods whose labels match the selector |
| **Deployment** | Manages (and counts) only Pods with matching labels |
| **ReplicaSet** | Makes sure exactly N Pods with specific labels run |
| **NetworkPolicy** | Allows/denies network traffic based on Pod labels |
| **HorizontalPodAutoscaler** | Scales Deployments identified by label |

**Example:** a Service with the selector `app: chromium` forwards requests exclusively to Pods that
carry the label `app: chromium` -- regardless of which node they run on.

```yaml
# Service
spec:
  selector:
    app: chromium       # <-- matches all Pods with this label
```

```yaml
# Pod (must have this label for the Service to find it)
metadata:
  labels:
    app: chromium
```

#### Filtering and queries

Labels let you filter resources with `kubectl` in a targeted way, without searching every object:

```bash
# List all Pods with the label app=chromium.
kubectl get pods -l app=chromium

# Filter Pods by multiple conditions.
kubectl get pods -l app=chromium,environment=training

# List all Deployments for a specific team.
kubectl get deployments -l team=devops
```

#### Organisation and governance

In larger environments labels help you keep an overview:

- **`app`** – name of the application
- **`version`** – version number (e.g. for canary Deployments)
- **`environment`** – `dev`, `staging`, `production`
- **`team`** – owning team
- **`managed-by`** – tool that manages the resource (e.g. `helm`)

Many tools (Helm, Argo CD, Prometheus, Grafana) rely on standardised labels to detect and map
resources automatically.

### Labels vs. annotations

Labels often get confused with **annotations**. The difference stays clear:

| | Labels | Annotations |
|---|---|---|
| **Purpose** | Selection & grouping | Additional information (for humans/tools) |
| **Use in selectors** | ✅ Yes | ❌ No |
| **Example** | `app: chromium` | `description: "Chromium Browser for Training"` |

> 💡 **Rule of thumb:** when another resource should *react* to it → label. When it only *describes*
> information → annotation.

---

### Labels in practice -- common mistakes

> ⚠️ **WATCH OUT** -- a very common beginner mistake: the label selector of a Deployment and the
> labels of the created Pods **must match**. When they differ, the Deployment does not recognise its
> own Pods and keeps starting new ones -- until the cluster fills up.

```yaml
spec:
  selector:
    matchLabels:
      app: chromium     # <-- must match ...
  template:
    metadata:
      labels:
        app: chromium   # <-- ... this label
```

## YAML & declarative

### Comparison

| Approach       | Description                 | Example                            |
| -------------- | --------------------------- | ---------------------------------- |
| **Imperative** | "Do this now"               | `kubectl create deployment ...`    |
| **Declarative**| "Desired target state"      | `kubectl apply -f deployment.yaml` |

In practice almost all work is declarative -- YAML manifests go into Git, get versioned and are
applied with `kubectl apply`.

### YAML basic structure

Every Kubernetes manifest has four main parts:

| Field        | Meaning                                                 |
| ------------ | ------------------------------------------------------- |
| `apiVersion` | API version of the resource (e.g. `v1`, `apps/v1`)       |
| `kind`       | Type of the resource (e.g. `Pod`, `Deployment`, `Service`) |
| `metadata`   | Metadata: name, Namespace, labels                        |
| `spec`       | Specification: the desired state                         |

### YAML rules

- Indentation with **spaces** (no tabs!)
- Lists start with `-`
- Key-value pairs with `:`
- Strings usually need no quotation marks

### kubectl explain

**Documentation directly on the command line:**

You will often wonder how a Kubernetes object is structured or which fields it has. With
`kubectl explain` you fetch the official documentation **directly on the command line** without
looking it up in the browser. The tool shows you the structure of Kubernetes resources, their fields
and their descriptions — very helpful when writing YAML manifests!

```bash
kubectl explain pod
kubectl explain pod.spec
kubectl explain pod.spec.containers
kubectl explain deployment.spec.strategy
```

### Creating Chromium declaratively

Now we create Chromium **declaratively** with a YAML file. That is clearly more maintainable because
the configuration can be versioned and shared in the team.

**One file per object -- and please check the name.** The files in this training are called
`<app>-<kind>.yaml`: lowercase, kebab-case, `<kind>` is the Kubernetes kind (`deployment`, `service`,
`config-map` -- not `configmap`). Variants of the same kind get a suffix
(`chromium-deployment-liveness.yaml`), objects without an app reference are called `<kind>.yaml`
only (`limitrange.yaml`).

> ⚠️ **Warning:** `kubectl apply -f <old-name>.yaml` applies the old manifest **silently** -- no
> error, no warning, only a Pod that looks different than expected. Check it beforehand with
> `kubectl diff -f <file>.yaml` and look after the apply with
> `kubectl get deployment chromium -n k8s-training -o yaml` at what really runs in the cluster.

File `chromium-deployment.yaml`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: chromium
  namespace: k8s-training
  labels:
    app: chromium
spec:
  replicas: 1
  selector:
    matchLabels:
      app: chromium
  template:
    metadata:
      labels:
        app: chromium
    spec:
      containers:
        - name: chromium
          image: lscr.io/linuxserver/chromium:latest
          resources:
            requests:
              cpu: "250m"
              memory: "512Mi"
            limits:
              cpu: "1"
              memory: "1Gi"
          ports:
            - containerPort: 3000
            - containerPort: 3001
          env:
            - name: PUID
              value: "1000"
            - name: PGID
              value: "1000"
            - name: TZ
              value: "Europe/Berlin"

```

**File `chromium-service.yaml`:**

```yaml
apiVersion: v1
kind: Service
metadata:
  name: chromium
  namespace: k8s-training
spec:
  type: NodePort
  selector:
    app: chromium
  ports:
    - name: http
      protocol: TCP
      port: 4000
      targetPort: 3000
```

**Apply:**

```bash
# Create the Deployment.
kubectl apply -f chromium-deployment.yaml

# Create the Service.
kubectl apply -f chromium-service.yaml

# Check the status.
kubectl get deployments
kubectl get services
kubectl get pods
```

> to document. With YAML files several developers can work together and version the configuration in
> Git.

Now add the volumes for `/dev/shm` so Chromium runs stably.
Chromium uses shared memory for rendering web pages. Without a
sufficiently large `/dev/shm` the browser crashes or shows empty pages. With `medium: Memory`
the volume lives in RAM -- fast and exactly right for temporary rendering data.

```yaml
apiVersion: v1
kind: Deployment
metadata:
  ...
spec:
  ...
    spec:
      containers:
        - name: chromium
          ...
          volumeMounts:
            - name: shm
              mountPath: /dev/shm
      volumes:
        - name: shm
          emptyDir:
            medium: Memory
            sizeLimit: 1Gi
```

Then apply it again:

```bash
kubectl apply -f chromium-deployment.yaml
```

With `kubectl get pods` you can check that the new Pod runs.

You can reach both containers from outside in several ways. You have already seen some of them:

- [ ] **Node IP** provides access through a port on one of the nodes. This is useful with an external

### Ingress route

<Image src={knba10050} alt="Service and Ingress * Created with Microsoft Copilot" />

When your cluster comes with a dashboard (for example Rancher), you can click the route together
there. The following instructions show the result that you then rebuild for the Code-Server: a route
from the host `chrome.k8s-training.frickeldave.de` to the Chromium Service.

- Service Discovery -> Ingresses -> Create
  - Namespace: k8s-training
  - Name: chromium-ingress
  - Rules:
    - Request Host: chrome.k8s-training.frickeldave.de
      - The host is freely chosen, but must be a valid DNS name -- wildcards only as the leftmost
        whole label (`*.k8s-training.frickeldave.de`), never in the middle of the name.
    - Path Prefix: /
    - Target Service: chromium
    - Port: 4000

Once the route exists, you open it in the browser via exactly this host. A Chromium window appears in
which you can open pages that are reachable inside the cluster only.

The result looks like this -- you can print it any time and use it as a template for the
Code-Server:

```bash
kubectl get ingress chromium-ingress -o yaml
```

Without a dashboard a dry run gets you to the same YAML. `--dry-run=client` builds the manifest
without applying it:

```bash
kubectl create ingress chromium-ingress --rule="chrome.k8s-training.frickeldave.de/*=chromium:4000" --dry-run=client -o yaml
```

### Creating an Ingress route via kubectl

As an alternative to the Rancher dashboard you can create the Ingress route directly with `kubectl`.

#### Imperative

Which **IngressClass** your cluster uses depends on the installation. Common values are `nginx`,
`traefik` and -- depending on the installation -- `traefik-ingress-controller`. Do not guess, but
ask the cluster:

```bash
kubectl get ingressclass
```

```bash
# Create the Code-Server Ingress.
kubectl create ingress code-server-ingress --rule="code.k8s-training.frickeldave.de/*=code-server:8443"

# Set the Ingress class afterwards -- use a value from `kubectl get ingressclass`.
# Candidates: nginx, traefik, traefik-ingress-controller.
kubectl patch ingress code-server-ingress --type=merge -p '{"spec":{"ingressClassName":"nginx"}}'
```

Anyone who does not issue the certificates for these hosts themselves quickly ends up with
[ACME](/docs/kubernetes-basis-en/90-glossary#acme): the protocol with which the Ingress Controller
requests and renews Let's Encrypt certificates automatically.

<Notice type="info">
  **Gateway API – the successor of Ingress**

  The classic `Ingress` resource (with `ingressClassName: nginx`) works well, but meanwhile counts as
  **outdated in its design**. The modern successor is the **Gateway API**
  (`gateway.networking.k8s.io`). It is more flexible, more role-based and splits the monolithic
  Ingress resource into several specialised resources (`Gateway`, `HTTPRoute`, `TLSRoute`, …). For
  getting started Ingress suffices completely – anyone building productive, complex routing scenarios
  should take a look at the Gateway API.
</Notice>

#### Declarative

Here a ready-made, fully spelled out file `code-server-ingress.yaml` -- the same shape you saw above
with `kubectl get ingress chromium-ingress -o yaml`:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: code-server-ingress
  namespace: k8s-training
spec:
  ingressClassName: nginx
  rules:
  - host: code.k8s-training.frickeldave.de
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: code-server
            port:
              number: 8443
```

When `kubectl get ingressclass` shows another name (`traefik`, `traefik-ingress-controller`), adjust
`ingressClassName` -- otherwise the controller rejects the route.

```bash
kubectl apply -f code-server-ingress.yaml
```
<br/>
<Notice type="info">
  **Why several small YAML files instead of one huge one?**

  You could of course pack Deployment, Service and Ingress for an application into a single YAML file
  (separated by `---`). In practice, however, **one file per resource** turned out the better choice:

  - **Fewer Git conflicts** – When two team members work on the Deployment and the Service at the same
    time, a conflict only arises when both change the same file. With separate files that does not
    happen.
  - **Lower token consumption** – AI tools and code reviewers only need to read the file that is
    relevant right now, not the whole app configuration at once.
  - **Better readability** – One file = one resource = one task. That makes review and
    troubleshooting easier.
  - **More flexible deployment strategy** – You can, for example, re-apply the Service without
    touching the Deployment, or update the Ingress only.
  - **Simpler automation** – CI/CD pipelines can deploy individual resources in a targeted way when
    only one file changed.
  - **Reusability** – The Service manifests independently of the Deployment and is easier to carry
    over into other projects or environments.

  **Rule of thumb:** one YAML file per Kubernetes resource (Deployment, Service, Ingress, ConfigMap,
  …). That keeps everything cleanly separated and eases teamwork.
</Notice>

### Determining the Ingress URL

```bash
# List all routes in the Namespace.
kubectl get ingress -n k8s-training

# Also show the host and ports on one line.
kubectl get ingress -n k8s-training -o wide

# Details: HOST, ADDRESS, default backend, and events.
kubectl describe ingress code-server-ingress -n k8s-training
```

Two columns decide whether the call works:

| Column      | Meaning                                                                                                                                      |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| **HOST**    | The name you call in the browser -- `code.k8s-training.frickeldave.de` here. It must point to the controller via DNS or `/etc/hosts`.         |
| **ADDRESS** | IP or hostname on which the Ingress Controller accepts the traffic. The field stays empty until the controller has seen the route.           |

In clusters that assign their hostnames themselves, the HOST often follows the scheme
`[hostname]-[namespace].[cluster].[domain]`. In this training it works the other way round: the host
comes from the rule you wrote and reads `code.k8s-training.frickeldave.de`.

**ADDRESS stays empty?** Then check whether an Ingress Controller runs at all
(`kubectl get ingressclass`) and whether `ingressClassName` matches it. An empty ADDRESS does not
automatically mean a broken route -- often only the DNS entry is missing.

Without a DNS entry you test the route directly against the controller. `-H 'Host: …'` sends the
hostname in the header, `--resolve` resolves the name locally to the controller IP:

```bash
# Option 1: set the Host header.
curl -H 'Host: code.k8s-training.frickeldave.de' http://<ADDRESS>/

# Option 2: resolve the name locally to the controller IP.
curl --resolve code.k8s-training.frickeldave.de:80:<ADDRESS> http://code.k8s-training.frickeldave.de/
```

```bash
kubectl logs <pod>                              # Read logs
kubectl logs -f <pod>                           # Follow logs live
kubectl apply -f <file.yaml>                    # Create or update
kubectl delete -f <file.yaml>                   # Delete
kubectl delete <resource> <name>                # Delete a single resource
kubectl set env deployment/<name> KEY=VALUE     # Set an environment variable
kubectl explain <resource>                      # Show documentation
kubectl get pods -w                             # Watch Pods live
kubectl get ingress                             # List Ingress routes
kubectl create ingress <name> --rule="..."      # Create an Ingress route (imperative)
kubectl get all -n <namespace>                  # List all resources in the Namespace
```
