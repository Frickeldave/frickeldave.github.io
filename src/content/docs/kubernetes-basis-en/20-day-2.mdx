## ConfigMaps

So far configuration values such as `PUID`, `PGID`, `TZ` and the Code-Server password sit directly in
the Deployment YAMLs from Day 1. That stays maintainable as long as only one Deployment is affected --
but with the second Deployment at the latest the values repeat.

<Image src={knba20010} alt="ConfigMaps * Created with OpenAI Imagegen" />

A **ConfigMap** is a Kubernetes object that stores configuration data as key-value pairs and passes it
to containers -- either as an **environment variable** or as a **file** (through a volume).

### Central linuxserver ConfigMap

The linuxserver.io images almost always query the same three values: user ID, group ID and time zone.
Instead of typing them into every Deployment, we store them once, centrally -- one ConfigMap for all
applications that need these values.

File `linuxserver-common-config-map.yaml`:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: linuxserver-common
  namespace: k8s-training
data:
  PUID: "1000"
  PGID: "1000"
  TZ: "Europe/Berlin"
```

<br/>
```bash
kubectl apply -f linuxserver-common-config-map.yaml
```

You bind it with `envFrom` -- that imports all three keys as environment variables:

```yaml
envFrom:
  - configMapRef:
      name: linuxserver-common
```

The order counts: create the ConfigMap first, then the Deployment. A Pod that references a missing
ConfigMap does not start and stays with `CreateContainerConfigError`.

### Example: externalising the Code-Server workspace

The Code-Server from Day 1 carries the environment variable `DEFAULT_WORKSPACE` hard-coded in the
YAML:

```yaml
env:
  - name: DEFAULT_WORKSPACE
    value: "/config/workspace"
```

We now move that into a ConfigMap.

**1. Create the ConfigMap**

File `code-server-config-map.yaml`:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: code-server-config
  namespace: k8s-training
data:
  DEFAULT_WORKSPACE: "/config/workspace"
```

<br/>
```bash
kubectl apply -f code-server-config-map.yaml
```

**2. Use the ConfigMap in the Deployment**

One key suffices for the workspace. `PUID`, `PGID` and `TZ` live in the central ConfigMap
`linuxserver-common` from above -- the Deployment binds both via `envFrom`:

```yaml
envFrom:
  - configMapRef:
      name: linuxserver-common     # PUID, PGID, TZ
  - configMapRef:
      name: code-server-config     # DEFAULT_WORKSPACE
```

The Deployment then looks like this (excerpt):

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: code-server
  namespace: k8s-training
spec:
  # ... selector, template etc. ...
  template:
    spec:
      containers:
        - name: code-server
          image: lscr.io/linuxserver/code-server:latest
          resources:
            requests:
              cpu: "250m"
              memory: "512Mi"
            limits:
              cpu: "1"
              memory: "1Gi"
          ports:
            - containerPort: 8443
          envFrom:                          # two ConfigMaps as environment variables
            - configMapRef:
                name: linuxserver-common
            - configMapRef:
                name: code-server-config
          env:
            - name: PASSWORD                # The Secret is still hard-coded for now.
              value: "trainingk8s"
```

<br/>
```bash
kubectl apply -f code-server-deployment-configmap.yaml
```

**Important:** `envFrom` imports **all** keys of a ConfigMap as environment variables.
`DEFAULT_WORKSPACE` becomes the variable `DEFAULT_WORKSPACE`, `PUID`, `PGID` and `TZ` come from
`linuxserver-common` unchanged. When the same key exists in both ConfigMaps, the **last** entry wins
-- therefore the order stays `linuxserver-common` before `code-server-config`.

### ConfigMapKeyRef for a single value from a ConfigMap

Instead of loading a complete ConfigMap, you can also load a single value from a ConfigMap.

spec:
...
    spec:
      containers:
          ...
          env:
            - name: LOG_LEVEL
              valueFrom:
                configMapKeyRef:
                  name: app-config
                  key: LOG_LEVEL

### ConfigMap as a volume (file)

Besides environment variables a ConfigMap can also be mounted into the container as a **volume**.
Every key then becomes its own file. That is handy for configuration files such as `nginx.conf`,
`prometheus.yml` or `vector.toml`.

```yaml
volumes:
  - name: config-volume
    configMap:
      name: app-config
```

Inside the container the file `/etc/config/DEFAULT_WORKSPACE` then appears with the content
`/config/workspace`. We apply this pattern directly in the sidecar exercise.

<Notice type="info">
  **ConfigMap changed, Pod keeps running? That is what Reloader is for.**

  A Deployment does not restart by itself after a ConfigMap change.
  [Reloader](https://github.com/stakater/Reloader) is a small controller that watches ConfigMaps and
  Secrets and lets the affected workload roll out again via an annotation. You install it from the
  Stakater Helm repository or via the release manifest from the project; both need cluster rights and
  run once. Afterwards the annotation on the Deployment suffices:

  ```yaml
  metadata:
    annotations:
      reloader.stakater.com/auto: "true"
  ```

  Without the annotation nothing happens -- Reloader works opt-in per workload.

  **Different with volume mounts:** when the ConfigMap is mounted as a volume, the files inside the
  container get **updated automatically** (with a slight delay, usually < 1 minute). The application
  itself must notice or re-read the file change.

</Notice>

**Summary**

| Method | Description | Use |
|---------|-------------|---------|
| `envFrom` + `configMapRef` | All keys as environment variables | Several Deployments share configuration |
| `valueFrom.configMapKeyRef` | Single key as environment variable | Selective binding |
| Volume mount | ConfigMap as files in the file system | Configuration files for tools (Vector, nginx, ...) |

**Remember:** ConfigMaps serve **non-sensitive** data. Passwords, tokens and certificates belong in
Secrets.

### Secret: externalising the Code-Server password

The Code-Server password still sits hard-coded in the Deployment. We now move it into a
[Secret](/docs/kubernetes-basis-en/90-glossary#secret).

**1. Create the Secret**

File `code-server-secret.yaml`:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: code-server-secret
  namespace: k8s-training
type: Opaque
stringData:
  PASSWORD: "trainingk8s"
```
<br/>
```bash
kubectl apply -f code-server-secret.yaml
```

**2. Check the Secret**

```bash
kubectl get secret code-server-secret -n k8s-training -o yaml
```

The output shows `PASSWORD: dHJhaW5pbmcya3M=` – that is Base64 encoded, not encrypted:

```bash
echo "dHJhaW5pbmcya3M=" | base64 -d
# Output: trainingk8s
```

```powershell
[System.Text.Encoding]::UTF8.GetString([System.Convert]::FromBase64String("dHJhaW5pbmcya3M="))
# Output: trainingk8s
```
<br/>

<Notice type="info">

**💡 The most common question: "why is Base64 no security disaster then?"**

Base64 is no encryption, only an encoding – like another spelling. That is intentional: Secrets must
stay machine-readable and must not contain special characters that break YAML or env variables.

The real security lives not in the encoding, but in these mechanisms:

| Mechanism | Effect |
|-------------|---------|
| **RBAC** | Only authorised people/systems may run `kubectl get secret` |
| **Encryption at rest** | The cluster encrypts Secrets on disk (enabled by default since Kubernetes 1.13+) |
| **Encryption in transit** | API communication runs over TLS – nobody can read the traffic along the way |
| **No Git** | Secrets never get committed in YAML files, but stored in the cluster only |
| **stringData** | You provide the password in plain text – only Kubernetes itself encodes it to Base64 |

**In short:** the Base64 "protection" is an encoding for data transport, not a security feature. The
protection comes from RBAC, TLS and encryption in the cluster. Anyone allowed to run
`kubectl get secret` also reaches the values – and exactly that needs steering through permissions.

</Notice>
<br/>

**3. Use the Secret in the Deployment**

Instead of `value: "trainingk8s"` we reference the value from the Secret:

```yaml
env:
  - name: PASSWORD
    valueFrom:
      secretKeyRef:
        name: code-server-secret
        key: PASSWORD
```
<br/>
```bash
kubectl apply -f code-server-deployment-configmap-secret.yaml
```

**Important:** create the Secret **in the same Namespace** as the Pod. Adjust it accordingly when the
Namespace differs (e.g. `k8s-prod` instead of `k8s-training`).

## Pods and container types

So far we only met Pods as simple container wrappers. In fact Pods can hold several containers that
share the same network namespace and the same volumes. This concept serves to deploy and manage
tightly coupled processes together.

### Container types

| Type                  | Purpose                                 | Lifetime                      |
| --------------------- | --------------------------------------- | ----------------------------- |
| [**App container**](/docs/kubernetes-basis-en/90-glossary#app-container)     | Main application                        | Runs permanently              |
| [**Init container**](/docs/kubernetes-basis-en/90-glossary#init-container)    | Initialisation before the app starts    | Runs once until completion    |
| [**Sidecar container**](/docs/kubernetes-basis-en/90-glossary#sidecar-container) | Supporting services (logging, proxy)    | Runs permanently next to the app |

**Rule:** several containers in the same Pod only when they are tightly coupled. Otherwise use
separate Pods. The containers of ONE app here are NOT tightly coupled, but only loosely connected via
Services and Ingress. Therefore we deploy them in separate Pods.

### Analogy: container types in the logistics company

To understand the different container types better, consider them in the context of a logistics
company that delivers parcels worldwide:

**App container = main transport vehicle**
The app container is like the main transport vehicle (e.g. a truck or a plane) that delivers the
actual freight to the destination. It is the heart of the delivery process and performs the main task:
bringing the parcel from sender to recipient. This vehicle stays active during the whole trip and
makes sure the shipment reaches its destination.

**Init container = preparatory logistics services**
Init containers correspond to the necessary preparation services that must happen before every
transport. Before a parcel can even be shipped, several steps must follow one after another:
- The shipment is accepted and registered at the origin
- Customs formalities are handled
- The optimal route is calculated and booked
- The means of transport is prepared and fuelled
Each of these steps must complete fully before the main transport can start. Only when all init
containers finished their work can the app container begin the actual transport.

**Sidecar container = accompanying services during transport**
Sidecar containers are like the supporting services that accompany the main transport and help
continuously:
- GPS tracking sends position data to the headquarters all the time
- Temperature monitoring checks continuously whether cooling conditions hold
- Security services watch the parcel for tampering attempts
- Communication systems keep contact with the control centre
These services run at the same time as the main transport and provide transparency, safety and
efficiency without transporting the freight themselves.

### Init containers

Init containers start sequentially in the order of their definition, before the app containers start.
Each one must complete successfully. This serves as a preview only; we use the concept later.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app-mit-init
  namespace: k8s-training
spec:
  initContainers:
    - name: wait-for-db
      image: busybox:1.28
      command:
        - sh
        - -c
        - 'until nslookup my-database.k8s-training.svc.cluster.local; do echo "Warte auf DB...";
          sleep 2; done'
  containers:
    - name: app
      image: nginx:1.27
      ports:
        - containerPort: 80
```

Typical use cases:

- Waiting for a database or an external service
- Preparing configuration files
- Running schema migrations

### Sidecar containers

Sidecar containers run permanently next to the main application and share network and volumes.
Typical patterns:

| Pattern | Description | Example |
|---------|-------------|----------|
| **Log shipper** | Reads the logs of the app and sends them to a central logging platform | Vector, Fluent Bit, Promtail |
| **Reverse proxy** | Takes over SSL termination, auth or rate limiting for the app | nginx, Envoy, oauth2-proxy |
| **Metrics exporter** | Collects metrics of the app and exposes them for Prometheus | nginx-prometheus-exporter, node-exporter |
| **Service mesh** | Takes over the entire network communication (TLS, tracing, retries) | Envoy (Istio), Linkerd proxy |

#### Exercise: Chromium with Vector as a sidecar

> **Deep dive:** in the ConfigMap chapter above you learned how ConfigMaps work as environment
> variables (`envFrom`). Here comes the second variant: **ConfigMap as a volume** -- the key
> `vector.toml` becomes the file `/etc/vector/vector.toml` inside the container.

In this exercise we equip **our Chromium** with a Vector sidecar.
Chromium (linuxserver.io) writes logs to `/config/log/` -- the sidecar reads these logs and prints
them as JSON on the console. Both containers share an `emptyDir` volume.

<br/>

**1. Create the ConfigMap for the Vector configuration**

File `vector-config-map.yaml`:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: vector-config
  namespace: k8s-training
data:
  vector.toml: |
    [sources.chromium_logs]
      type = "file"
      include = ["/config/log/*.log"]
      read_from = "beginning"

    [sinks.console]
      type = "console"
      inputs = ["chromium_logs"]
      encoding.codec = "json"
```
<br/>
```bash
kubectl apply -f vector-config-map.yaml
```
<br/>

**2. Extend the Chromium Deployment with a sidecar**

The existing Deployment from Day 1 (`chromium-deployment.yaml`) gets a second container and a shared
volume. In addition `envFrom` replaces the three individual `env` entries (`PUID`, `PGID`, `TZ`) with
the ConfigMap `linuxserver-common` from above. The changes are marked with `# NEU`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: chromium
  namespace: k8s-training
  labels:
    app: chromium
spec:
  replicas: 1
  selector:
    matchLabels:
      app: chromium
  template:
    metadata:
      labels:
        app: chromium
    spec:
      containers:
        - name: chromium
          image: lscr.io/linuxserver/chromium:latest
          resources:
            requests:
              cpu: "250m"
              memory: "512Mi"
            limits:
              cpu: "1"
              memory: "1Gi"
          ports:
            - containerPort: 3000
            - containerPort: 3001
          envFrom:                          # PUID, PGID, TZ
            - configMapRef:
                name: linuxserver-common
          volumeMounts:
            - name: shm
              mountPath: /dev/shm
            - name: chromium-logs          # NEW: shared log volume
              mountPath: /config/log
        - name: vector                     # NEW: sidecar container
          image: timberio/vector:0.42.0-alpine
          resources:
            requests:
              cpu: "50m"
              memory: "64Mi"
            limits:
              cpu: "200m"
              memory: "128Mi"
          command:
            - vector
            - --config
            - /etc/vector/vector.toml
          volumeMounts:
            - name: chromium-logs          # NEW: same volume as Chromium
              mountPath: /config/log
            - name: vector-config
      volumes:
        - name: shm
          emptyDir:
            medium: Memory
            sizeLimit: 1Gi
        - name: chromium-logs              # NEW: shared emptyDir for logs
          emptyDir: {}
        - name: vector-config              # NEW: ConfigMap mounted as a volume
          configMap:
            name: vector-config
```
<br/>
```bash
kubectl apply -f chromium-deployment-sidecar.yaml
```
<br/>

**3. Check that it works**

```bash
# Wait for the new Pod to run.
kubectl get pods -l app=chromium -w

# Show the sidecar logs.
kubectl logs -l app=chromium -c vector

# Show the log file in the Chromium container (the same source Vector reads).
kubectl exec -c chromium deploy/chromium -- cat /config/log/chromium.log

# Open Chromium in the browser and visit a few pages,
# then check the sidecar logs again:
kubectl logs -l app=chromium -c vector --tail=10
```
<br/>

**4. What happens here?**

- Chromium should write the logs to `/config/log/` (e.g. `chromium.log`, `Xorg.log`)
- The sidecar (`vector`) reads **the same files**
- Vector parses the logs and prints them as JSON on the console
- **Important:** both containers run in the same Pod -- they share network (`localhost`) and volume
- The sidecar joined an existing Deployment **afterwards** -- Kubernetes restarts the Pod
  automatically with both containers

<br/>

**5. Typical observation: Vector runs, but shows no logs?**

```bash
kubectl logs -l app=chromium -c vector
```

You see Vector starting and the healthcheck succeeding:

```
INFO vector::app: Vector has started.
INFO vector::topology::builder: Healthcheck passed.
INFO vector::sources::file: Starting file server. include=["/config/log/*.log"] exclude=[]
```

But **no JSON logs** arrive. That is **not** an error in your configuration – it comes from how the
Chromium image handles its logs.

**Why?** The linuxserver/chromium image starts Chromium via the script `/usr/bin/wrapped-chromium`.
The last line there redirects **all** output to `/dev/null`:

```bash
${BIN} \
  --no-sandbox \
  --password-store=basic \
  --simulate-outdated-no-au='Tue, 31 Dec 2099 23:59:59 GMT' \
  --start-maximized \
  --test-type \
  --user-data-dir \
  ${WAYLAND} \
   "$@" > /dev/null 2>&1
```

So Chromium **never** writes logs into files – neither to `/config/log/` nor anywhere else. The
container logs you see with `kubectl logs -c chromium` come from s6-overlay, not from Chromium
itself.

**Solution:** we replace the `wrapped-chromium` script with a custom version that writes logs both to
`/config/log/chromium.log` and to stdout. To do that we mount the adjusted script via ConfigMap with
`subPath` over the original script.
<br/>

**6. Enabling logging: custom startup script**

File `chromium-logging-config-map.yaml`:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: chromium-logging
  namespace: k8s-training
data:
  wrapped-chromium: |
    #!/bin/bash

    BIN=/usr/bin/chromium
    LOGFILE=/config/log/chromium.log

    # Cleanup
    if ! pgrep chromium > /dev/null;then
      rm -f $HOME/.config/chromium/Singleton*
    fi

    # Wayland check
    WAYLAND=""
    if ls -l /dev/dri/* > /dev/null 2>&1; then
      if pgrep labwc > /dev/null 2>&1; then
        WAYLAND="--ozone-platform=wayland"
      fi
    fi

    # Start Chromium with logs written to both a file and stdout.
    ${BIN} \
      --no-sandbox \
      --password-store=basic \
      --simulate-outdated-no-au='Tue, 31 Dec 2099 23:59:59 GMT' \
      --start-maximized \
      --test-type \
      --user-data-dir \
      ${WAYLAND} \
       "$@" > >(tee -a ${LOGFILE}) 2>&1
```
<br/>
```bash
kubectl apply -f chromium-logging-config-map.yaml
```
<br/>

**7. Update the Deployment**

The Chromium Deployment gets an additional volume mount that lays the ConfigMap script over the
original `wrapped-chromium`. Important: `subPath` mounts the single file only without covering the
rest of the directory. `defaultMode: 0755` makes the script executable.

File `chromium-deployment-sidecar-wrapped.yaml`

```yaml
apiVersion: apps/v1
kind: Deployment
      ...
spec -> templates -> spec -> containers -> volumeMounts:
            - name: shm
              mountPath: /dev/shm
            - name: chromium-logs
              mountPath: /config/log
            - name: chromium-logging-script     # NEW: custom wrapped Chromium command
              mountPath: /usr/bin/wrapped-chromium
              subPath: wrapped-chromium
      volumes:
        - name: shm
          ...
        - name: chromium-logging-script         # NEW: ConfigMap containing the script
          configMap:
            name: chromium-logging
            defaultMode: 0755
```
<br/>
```bash
kubectl apply -f chromium-deployment-sidecar-wrapped.yaml
```
<br/>

**8. Check that it works**

```bash
# Wait for the new Pod to run.
kubectl get pods -l app=chromium -w

# Show the sidecar logs -- JSON logs should appear now.
kubectl logs -l app=chromium -c vector --tail=10

# Check whether the log file exists in the container.
kubectl exec -c chromium deploy/chromium -- ls -la /config/log/

# Follow the Chromium logs live.
kubectl logs -l app=chromium -c vector -f
```

**Expected output from Vector:**

```json
{"file":"/config/log/chromium.log","host":"chromium-...","message":"[381:411:0719/...:ERROR:...] Registration response error message: DEPRECATED_ENDPOINT","source_type":"file","timestamp":"2026-07-19T..."}
{"file":"/config/log/chromium.log","host":"chromium-...","message":"DevTools listening on ws://...","source_type":"file","timestamp":"2026-07-19T..."}
```

Now Vector streams the Chromium logs as structured JSON – ready for further processing by
Elasticsearch, Loki or another logging platform.

**Note:** the logs now also contain Chromium internals such as `ERROR`, `WARNING` and `INFO`
messages. That is normal – Chromium logs many internal operations (GPU, network, extensions). In
production you could filter specific log levels or components with Vector transforms (`[transforms]`).

#### Production alternatives

Vector only serves as an example. Production environments often use these tools as a logging
sidecar:

| Tool | Size | Speciality |
|------|-------|-------------|

## Requests & limits

Picture several departments working side by side in the logistics centre.
Every department needs a certain amount of space and certain machines.

<Image src={knba20020} alt="Requests and limits * Created with OpenAI Imagegen" />


- **Without any agreement** one department would simply block the whole storage space, occupy the
  forklifts permanently and consume the power of everyone else. Chromium is such a department – a
  memory hog that soaks up the whole node without limits until other Pods starve.

- **`requests`** is the **minimum guarantee**: "This department gets at least
  3 shelf rows and 1 forklift – nobody may take that away." The
  warehouse manager (scheduler) places the department only when enough space is free.

- **`limits`** is the **upper bound**: "This department must not use more than 6 shelf rows and
  2 forklifts – even when space would be left." That way enough stays
  available for everyone else.

**In short:** without `requests` a department can starve because
another one blocks everything. Without `limits` a department can paralyse the whole warehouse.
Requests and limits provide **fairness and stability** in the logistics centre.

- **`requests`** – minimum guarantee. The scheduler places the Pod only on a node
  that has this amount free for sure.
- **`limits`** – upper bound. CPU gets throttled when exceeded, memory causes
  an OOM kill.

> **OOM = Out Of Memory.** When a container exceeds its `limits.memory`, the
> Linux kernel sends the signal `SIGKILL` (exit code 137). The container stops immediately and
> the Deployment restarts it automatically. When that keeps happening, it ends in
> `CrashLoopBackOff`.

The gap between requests and limits determines the [QoS class](#qos-classes) and thereby
how much priority the Pod receives when the node runs under pressure.

| Concept      | Description                                                                      |
| ------------ | -------------------------------------------------------------------------------- |
| [**requests**](/docs/kubernetes-basis-en/90-glossary#resource-limits) | Minimum guarantee -- the scheduler places the Pod only on nodes with enough resources |
| [**limits**](/docs/kubernetes-basis-en/90-glossary#resource-limits)   | Upper bound -- CPU gets throttled, memory overrun causes an OOM kill             |

**CPU units:** `1` = 1 core, `500m` = 0.5 cores, `250m` = 0.25 cores.

<Notice type="info">

**💡 The `m` stands for "milli"** – one thousandth of a core. `1000m` = 1 full core.
A container can get at most as many millicores as the node has cores.
Values above `1000m` (e.g. `2000m`) only make sense on a node with at least 2 cores.

</Notice>

**Memory units:** `128Mi` = 128 mebibytes, `1Gi` = 1 gibibyte.

<Notice type="info">

**💡 `Mi` and `Gi` stand for "mebi" and "gibi"** – binary units (base 1024).
`1 Mi` = 1024 × 1024 bytes = 1,048,576 bytes (as opposed to `1 MB` = 1,000,000 bytes).
Kubernetes always calculates in binary. Memory aid:

- `i` = binary (Mi, Gi, Ti) – that is the Kubernetes standard
- Letter only = decimal (M, G, T) – accepted by Kubernetes as well, but interpreted as binary

| Unit | Bytes | Rounded |
|---------|-------|----------|
| `128Mi` | 134,217,728 | ~128 MB |
| `256Mi` | 268,435,456 | ~256 MB |
| `512Mi` | 536,870,912 | ~512 MB |
| `1Gi`   | 1,073,741,824 | ~1 GB |
| `5Gi`   | 5,368,709,120 | ~5 GB |

</Notice>

### QoS classes

**Analogy to the logistics centre:**

The QoS class says: "How important is this department when space runs short?"

<Image src={knba20021} alt="QoS * Created with OpenAI Imagegen" />

- **BestEffort** – a department that never registered how much space it needs.
  When the warehouse fills up, it leaves first.
- **Burstable** – a department that reserved 3 shelf rows but may use up to 6.
  As long as space remains, it gets the extra rows. When things get tight, it has to fall back
  to its reserved 3.
- **Guaranteed** – a department that reserved exactly 3 shelf rows and may not use more.
  It is plannable and touched last.

| [QoS class](/docs/kubernetes-basis-en/90-glossary#qos-classes)     | Condition                               | Eviction priority            | Analogy |
| -------------- | --------------------------------------- | ---------------------------- | -------- |
| **Guaranteed** | requests == limits (for CPU and memory) | Lowest (evicted last)        | Firm commitment: exactly 3 shelf rows |
| **Burstable**  | requests < limits                       | Medium                       | Flexible: 3 reserved, up to 6 |
| **BestEffort** | No requests/limits set                  | Highest (evicted first)      | No reservation, cleared first |

**Remember:** the more precisely you know requests and limits, the more plannable your Pod becomes.
`Guaranteed` is the royal road for productive workloads – the Pod only gets evicted when absolutely
no other way out remains.

### Resource limits

The Deployment of Chromium still runs without resource declarations. We change that now.

**Note:** you do not configure the QoS class directly – it follows automatically
from the ratio of `requests` and `limits`:

| Constellation | QoS class |
|---|---|
| `requests` < `limits` | **Burstable** |
| `requests` == `limits` | **Guaranteed** |
| No `resources` | **BestEffort** |

File `chromium-deployment-res.yaml` -- add the `resources` block in the container.
The rest of the Deployment stays:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: chromium
  namespace: k8s-training    # ⬅️ Adjust the Namespace if needed.
  labels:
    app: chromium
spec:
  # ... replicas, selector, template (unchanged) ...
  template:
    spec:
      containers:
        - name: chromium
          # ... image, ports, envFrom (linuxserver-common), volumeMounts (unchanged) ...
          resources:                          # ⬅️ NEW
            requests:
              cpu: "250m"
              memory: "512Mi"
            limits:
              cpu: "1000m"
              memory: "1Gi"
```

```bash
kubectl apply -f chromium-deployment-res.yaml
```

### LimitRange

A [LimitRange](/docs/kubernetes-basis-en/90-glossary#limitrange) sets default values for all
containers in the Namespace that declare no resources of their own -- the safety net against forgotten
`resources` blocks.

<Notice type="warning">

**⚠️ Attention:** a LimitRange is **namespace-scoped** -- Namespace admin rights suffice. On
corporate clusters RBAC or a ResourceQuota often blocks creation anyway; in that case you skip this
step and set the resources directly in the Deployment, as we did with Chromium. A ResourceQuota can
reject the apply with `exceeded quota`. `kubectl describe limitrange default-container-resources`
shows the effective defaults.

</Notice>

File `limitrange.yaml`:

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: default-container-resources
  namespace: k8s-training
spec:
  limits:
    - type: Container
      default:
        cpu: "1"
        memory: "1Gi"
      defaultRequest:
        cpu: "100m"
        memory: "256Mi"
      max:
        cpu: "2"
        memory: "2Gi"
      min:
        cpu: "50m"
        memory: "32Mi"
```

<br/>
```bash
kubectl apply -f limitrange.yaml

# Show the effective defaults and limits.
kubectl describe limitrange default-container-resources -n k8s-training
```

## Health checks

Kubernetes does not know automatically whether an application really works -- only whether a container
runs. Health checks (probes) give Kubernetes that intelligence: they check the state of a container
regularly and trigger automatic actions when something goes wrong.

### Probe types

Picture a logistics company: a truck driver delivers parcels. Kubernetes is the dispatcher who makes
sure everything runs smoothly.

<Image src={knba20030} alt="Health checks * Created with OpenAI Imagegen" />


- **Liveness probe** – *"Is the driver still alive?"*
  The dispatcher calls every few minutes. When nobody answers, they send a replacement driver
  (container restart). The driver may also just be in the toilet briefly --
  replacement happens only after several failed attempts.

- **Readiness probe** – *"Can the driver accept a parcel right now?"*
  The driver is stuck in traffic → no parcel acceptance → the dispatcher gives the tour to another
  driver (Pod removed from Service endpoints). Once the traffic jam is over, they get scheduled
  again.

- **Startup probe** – *"Did the driver load the truck and check the route?"*
  Before the first tour the dispatcher asks: "Are you ready to go?" Only when "Yes" comes back do the
  regular liveness/readiness checks begin. A truck still loading should not be called all the time.

| Probe               | Question                              | Action on failure                          |
| ------------------- | ------------------------------------- | ------------------------------------------ |
| [**Liveness probe**](/docs/kubernetes-basis-en/90-glossary#liveness-probe)  | Does the application still run?       | Container gets restarted                   |
| [**Readiness probe**](/docs/kubernetes-basis-en/90-glossary#readiness-probe) | Can the application accept traffic?   | Pod gets removed from Service endpoints    |
| [**Startup probe**](/docs/kubernetes-basis-en/90-glossary#startup-probe)   | Did the application finish starting?  | Liveness/readiness paused until startup OK |



### Probe mechanisms

| Mechanism   | Description                                    |
| ----------- | ---------------------------------------------- |
| `httpGet`   | HTTP GET to path+port; status 200-399 = healthy |
| `exec`      | Command inside the container; exit code 0 = healthy |
| `tcpSocket` | Checks whether the TCP port is open            |

### Parameters

| Parameter             | Description                    | Default |
| --------------------- | ------------------------------ | -------- |
| `initialDelaySeconds` | Wait time before the first check | 0      |
| `periodSeconds`       | Interval between checks        | 10       |
| `timeoutSeconds`      | Timeout per check              | 1        |
| `successThreshold`    | Successes until "healthy"      | 1        |
| `failureThreshold`    | Failures until "unhealthy"     | 3        |

### Why linuxserver.io images are so robust

The images from linuxserver.io use **s6-overlay** as init system. It is no simple process starter,
but a full service manager — comparable to a mini systemd. s6-overlay watches all started processes
and restarts them **automatically** when they crash. That has far-reaching consequences for liveness
probes:

| Property | Effect |
|---|---|
| **Auto-restart** | When Chromium dies, s6 restarts it right away — often before Kubernetes triggers the liveness probe |
| **PID 1** | s6 runs as PID 1 and reaps zombie processes, preventing orphan processes |
| **Service dependencies** | Services start in the right order (e.g. Chromium only after X11/Wayland) |
| **Log redirect** | s6 redirects the logs of all services to stdout — that is why `kubectl logs` shows only s6 messages, not Chromium itself |

**Consequence for liveness probes:** with linuxserver images a liveness probe often stays
**ineffective** in the auto-restart case — s6 acts faster. The probe only takes effect when the whole
container hangs (process alive, but no response). That is no defect, but deliberate robustness.

## Applying probes

Now we configure probes for both applications. Chromium and Code-Server have different startup times
-- Chromium is memory- and rendering-intensive and needs clearly longer to start than Code-Server. The
probe configuration has to account for that, otherwise Kubernetes marks new containers as "unhealthy"
too early and restarts them endlessly. We extend the existing YAML manifests with `startupProbe`,
`livenessProbe` and `readinessProbe`.
<br/>
<Notice type="info">
Chromium comes predefined here, experiment with Code-Server.
</Notice>

### Chromium probes

Extend the file `chromium-deployment.yaml` (resources + probes):

```yaml
apiVersion: apps/v1
    ...
    spec:
      containers:
        - name: chromium
          ...
          startupProbe:
            httpGet:
              path: /
              port: 3000
            failureThreshold: 30
            periodSeconds: 10
          livenessProbe:
            httpGet:
              path: /
              port: 3000
            periodSeconds: 15
            failureThreshold: 3
          readinessProbe:
            httpGet:
              path: /
              port: 3000
            periodSeconds: 5
            failureThreshold: 1
```
<br/>
- StartupProbe (failureThreshold: 30, periodSeconds: 10) — Chromium needs up to 5 minutes to start. The
  startup probe says: "Stay calm as long as it runs, no panic." While the startup probe runs,
  liveness and readiness stay ignored.
- ReadinessProbe (failureThreshold: 1, periodSeconds: 5) — Chromium started, but the browser hangs
  right now (e.g. a page loads forever). The readiness probe fails → the Pod leaves the endpoints →
  no more traffic → Chromium can recover. The Pod does not die, it only loses traffic for a moment.
- LivenessProbe (failureThreshold: 3, periodSeconds: 15) — Chromium crashed (process dead, port does
  not answer). After 3 failures = 45 seconds Kubernetes says: "It is dead" and restarts the
  container.
<br/>

```bash
kubectl apply -f chromium-deployment-all-probes.yaml
```

**💡 What are EndpointSlices?**
A Service in Kubernetes distributes traffic across several Pods. To know which Pods stay reachable at
the moment, the Service manages a list of IPs + ports – the endpoints. `EndpointSlices` are the
modern version of that: they group this list into manageable blocks (slices) and update them live. As

</Notice>

## Deployment strategies

How Kubernetes replaces old Pods with new ones is no small matter -- configured wrongly it causes
downtime or data conflicts. Kubernetes offers two strategies; you choose between them depending on
the application type.

### Comparison

Picture a logistics fleet: you own 10 trucks and receive 10 new models.
How do you swap them?

<Image src={knba20040} alt="Deployment strategies * Created with OpenAI Imagegen" />


- **RollingUpdate** – *"One out, one in."*
  You send truck after truck into the workshop. While truck 1 gets converted, the other 9 keep
  driving. Once truck 1 is done, truck 2 follows. The fleet stays 90% operational at any time – no
  tour gets cancelled.

- **Recreate** – *"All into the workshop, then all new."*
  You bring all 10 trucks into the workshop at once. Only when all conversions finished do they
  return to the road. A short downtime, but the switch may be simpler,
  because you do not have to care about compatibility between old and new trucks.

| Strategy          | Behaviour                                    | Downtime | Use                                                   |
| ----------------- | -------------------------------------------- | ----------- | ----------------------------------------------------- |
| [**RollingUpdate**](/docs/kubernetes-basis-en/90-glossary#rollingupdate) | Pods get replaced step by step               | None        | Standard, production                                  |
| **Recreate**      | All old Pods stopped, then new ones started  | Brief       | When old + new version cannot run in parallel         |



### Configuration

```yaml
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1 # Maximum number of additional Pods allowed during the update.
      maxUnavailable: 0 # Maximum number of Pods that can be unavailable at once.
```

- `maxSurge: 1` -- during the update 1 Pod more than `replicas` may run
- `maxUnavailable: 0` -- no Pod may be missing (no traffic loss)


With the configured RollingUpdate strategy we now perform a real update -- and learn to roll back
immediately in a failure case. As an example we change the Chromium image to another version and
watch the process live.

## PVs & PVCs

Container file systems are volatile -- when a Pod dies, all data is gone. For applications such as
MariaDB that is no option. Persistent Volumes (PVs) and Persistent Volume Claims (PVCs) decouple
storage from the Pod lifetime.



### Analogy: the logistics warehouse

Picture running a logistics warehouse with several halls (nodes). Space abounds,
but not every space stays reachable at the same speed -- and not every one costs the same. Storage in
the cluster behaves exactly like that.

<Image src={knba20050} alt="PVs and PVCs * Created with OpenAI Imagegen" />

- **Without persistent storage** every work order (Pod) uses a disposable table: you put
  your boxes on it, but when the order finishes, the table gets thrown away –
  boxes included. Exactly that happens with `emptyDir`: the Pod dies, the data is
  gone.

- **A PersistentVolume (PV)** is like a **permanently installed shelf** in the hall. It
  stays there, independent of individual orders. The warehouse manager (admin) built it,
  or it was ordered automatically (dynamic provisioning).

- **A PersistentVolumeClaim (PVC)** is the **warehouse slip** that an employee (Pod)
  fills in: "I need a shelf with 1 metre of shelf width that I can use alone
  (`ReadWriteOnce`)." The warehouse manager checks whether a matching shelf (PV) stays free and
  assigns it to the employee.

- **The StorageClass** is the **catalogue with shelf types**: "shelf that is hard to reach
  (hard disk)", "shelf space at shoulder height near the entrance (SSD)", "cooling shelf (archive)".
  The employee only says which type they need – the StorageClass takes care that exactly such a
  shelf gets delivered and installed.

| Shelf type                            | Way through the hall       | Access time  | Cost       |
| ------------------------------------- | ------------------------- | ------------ | ---------- |
| Shelf that is hard to reach (hard disk) | long way, far back      | high         | cheap      |
| Shelf space at shoulder height near the entrance (SSD) | short way, at hand | low | more expensive |
| Cooling shelf (archive)               | rarely needed, far away   | very slow    | very cheap |

**In short:** PV = the shelf in the hall. PVC = the slip that reserves it.
StorageClass = the catalogue that decides which shelf gets delivered. The Pod works at the
shelf – and when the Pod leaves, the shelf stays, content included.

### Concepts

| Concept                         | Description                                                           |
| ------------------------------- | --------------------------------------------------------------------- |
| [**PersistentVolume (PV)**](/docs/kubernetes-basis-en/90-glossary#persistentvolume)       | A piece of storage in the cluster, provided by an admin or dynamically |
| [**PersistentVolumeClaim (PVC)**](/docs/kubernetes-basis-en/90-glossary#persistentvolumeclaim) | Request of a Pod for storage (size, access type)                      |
| [**StorageClass**](/docs/kubernetes-basis-en/90-glossary#storageclass)                | Defines how PVs get created dynamically (provisioner, parameters)     |

### StorageClass: which shelf gets delivered?

Before you write a PVC, take a look at the StorageClasses of your cluster:

```bash
kubectl get storageclass
```

The line with `(default)` is the class Kubernetes takes automatically when your PVC names no
`storageClassName`. The same query including the column explanation appears in
[03 Preparation](/docs/kubernetes-basis-en/03-preparation#get-storageclass) under the section
"get storageclass". Without a default class the PVC stays in `Pending` -- that is the most common
reason when a Pod waits for its volume forever.

When you do not want to guess, set the class explicitly. The name must match the `NAME` from the
table exactly:

```yaml
spec:
  storageClassName: <name-aus-kubectl-get-storageclass>
  accessModes:
    - ReadWriteOnce
```

**Failure pattern "PVC stays Pending":** the three commands show you who blocks:

```bash
kubectl get pvc -n k8s-training
kubectl describe pvc code-server-config -n k8s-training
kubectl get events -n k8s-training --sort-by=.metadata.creationTimestamp
```

`describe` names the reason under `Events` -- mostly `no persistent volumes available for this claim`
or a typo in the `storageClassName`. The events additionally reveal whether the provisioner rejected
the request.

### Access modes

A PVC defines **how** the volume may be mounted. The `accessModes` value steers that:

| Mode     | One Pod   | Several Pods on the same node  | Several nodes |
| -------- | --------- | ------------------------------ | -------------- |
| **RWO** (ReadWriteOnce)     | ✅        | ✅                              | ❌              |
| **RWOP** (ReadWriteOncePod) | ✅        | ❌                              | ❌              |
| **ROX** (ReadOnlyMany)      | ✅ Read   | ✅ Read                         | ✅ Read         |
| **RWX** (ReadWriteMany)     | ✅        | ✅                              | ✅              |

**Remember:** `RWO` allows write access from Pods on **one** node at a time (several Pods on the same
node may still write at the same time). `RWOP` is stricter and limits access to **exactly one Pod** in
the whole cluster. `RWX` allows write access from any number of Pods on any number of nodes -- but
that requires a storage provider that supports it (e.g. NFS), which most cloud block storage does not
offer.

### Lifecycle

```
PVC-Anforderung → StorageClass erstellt PV → Pod mountet PVC
```

1. A PVC gets created with the desired size and access type
2. The StorageClass provisions a matching PV automatically
3. The Pod references the PVC as a volume and mounts it

**Reminder of Day 1:** when you deleted the Code-Server Pod, the file you created was gone. That comes
from `emptyDir` volumes dying with the Pod. PVCs survive Pod restarts and even
Pod deletions.

### Exercise: experiencing volatility

Before we work with PVCs, feel for yourself what "volatile" means.

1. **Open Code-Server in the browser** and create any file in the workspace
   (e.g. `test.txt` with some content).

2. **Restart the Pod** -- delete the Pod, the Deployment creates a new one automatically:

   ```bash
   kubectl delete pod -l app=code-server -n k8s-training
   ```

3. **Wait** until the new Pod runs:

   ```bash
   kubectl get pods -l app=code-server -n k8s-training -w
   ```

4. **Reload Code-Server** -- the file is gone (possibly still open in the editor, browser cache). The
   workspace was mounted with `emptyDir` and does not exist anymore.

5. **Insight:** container file systems are volatile. Without persistent storage
   all data is lost after a Pod restart.

### Code-Server: PVC (persistent)

The Code-Server from Day 1 uses `emptyDir` for `/config` -- you saw that already in the
exercise "experiencing volatility" above. Now we upgrade it to a **PVC** so the
workspace survives Pod restarts.

Two things are needed: the PVC and an updated Deployment that uses the PVC instead of
`emptyDir`. The Service stays unchanged -- the Code-Server remains reachable under
the same address.

File `code-server-pvc.yaml`:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: code-server-config
  namespace: k8s-training
spec:
  # storageClassName: <name>   # Set this only when you intentionally want a different class.
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi
```

Without `storageClassName` Kubernetes takes the default class of the cluster. The line therefore stays
commented out -- activate it only when you need a specific class (names from
`kubectl get storageclass`).

The Deployment from Day 1 (`code-server-deployment.yaml`) gets one small change only:
instead of `emptyDir: {}` we reference the PVC. The rest stays identical.

**Old version (Day 1):**

```yaml
      volumes:
        - name: config
          emptyDir: {}
```

**New version with PVC:**

```yaml
      volumes:
        - name: config
          persistentVolumeClaim:
            claimName: code-server-config
```
<br/>
```bash
kubectl apply -f code-server-pvc.yaml
kubectl apply -f code-server-deployment-pvc.yaml
```

**Important:** the update restarts the Pod -- but because we had no PVC before, the workspace starts
empty on this first start. Only from now on the data stays.

### Persistence test: data survives the Pod restart

Check the PVC status:

```bash
kubectl get pvc -n k8s-training
```

The PVC should show the status `Bound`.

Now comes the decisive test: you create a file in the workspace, delete the Pod and check whether it
still exists when the new Pod runs.

```bash
# Create a file in the persistent volume.
kubectl exec $(kubectl get pod -l app=code-server -n k8s-training -o jsonpath='{.items[0].metadata.name}') -n k8s-training -- touch /config/workspace/test.txt

# Delete the Pod (the Deployment creates a new one).
kubectl delete pod -l app=code-server -n k8s-training

# Wait for the new Pod to run.
kubectl get pods -l app=code-server -n k8s-training -w

# Check that the file survived.
kubectl exec $(kubectl get pod -l app=code-server -n k8s-training -o jsonpath='{.items[0].metadata.name}') -n k8s-training -- ls /config/workspace/test.txt
```

**Insight:** before (exercise "experiencing volatility") the file was gone after the Pod restart --
now, with the PVC, it stays. PVCs survive Pod restarts, `emptyDir` does not.

## 🧪 Deep dive: init container for MariaDB wait time (optional)

In the sidecar exercise with Vector you saw how two containers start in parallel.
With MariaDB + phpMyAdmin it works differently: phpMyAdmin **needs** a running MariaDB,
otherwise it only shows an error page. An init container solves that: it runs **before** the
app containers and blocks until MariaDB is ready.

### Task

Extend the Deployment from the previous exercise with an **init container** that checks before the
start of phpMyAdmin whether MariaDB answers on `localhost:3306`. The init container
uses the official `mariadb:11` image and runs `mysqladmin ping`.

### Solution (step by step)

**1. Adjust the Deployment**

Insert an `initContainers` block into the Deployment. The init container sits on
the same level as `containers` and `volumes`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: database
  namespace: k8s-training
  labels:
    app: database
spec:
  replicas: 1
  selector:
    matchLabels:
      app: database
  template:
    metadata:
      labels:
        app: database
    spec:
      initContainers:                          # ⬅️ NEW: runs before the app containers
        - name: wait-for-mariadb
          image: mariadb:11
          resources:
            requests:
              cpu: "50m"
              memory: "32Mi"
            limits:
              cpu: "100m"
              memory: "64Mi"
          command:
            - sh
            - -c
            - |
              echo "Waiting for MariaDB on localhost:3306 ..."
              until mysqladmin ping -h localhost -u root -ptrainingk8s --silent; do
                echo "MariaDB is not ready yet -- waiting 2s ..."
                sleep 2
              done
              echo "MariaDB is ready!"
      containers:
        - name: mariadb
          # ... existing configuration ...
        - name: phpmyadmin
          # ... existing configuration ...
```

**What happens here?**

| Step | Description |
|---------|-------------|
| `image: mariadb:11` | The init container uses the official MariaDB image – it contains `mysqladmin` |
| `mysqladmin ping` | Checks whether the MariaDB server answers on `localhost:3306`. Exit code 0 = ready |
| `-h localhost` | MariaDB runs in the same Pod – therefore reachable via `localhost` |
| `-u root -ptrainingk8s` | Authentication with the root password from the Secret |
| `--silent` | Exit code only, no output |
| `until ...; do sleep 2; done` | Repeat the check every 2 seconds until MariaDB answers |
| `echo "MariaDB is ready!"` | As soon as MariaDB answers, the init container exits with code 0 |

**2. Update the Deployment**

```bash
kubectl apply -f database-deployment.yaml
```

**3. Observe what happens**

Open two terminals:

**Terminal 1 – Pod status live:**

```bash
kubectl get pods -l app=database -n k8s-training -w
```

You see:

```
NAME                        READY   STATUS     RESTARTS
database-xxx                0/2     Init:0/1   0       ← Init container is running
database-xxx                0/2     Init:0/1   0       ← Init container is waiting for MariaDB
database-xxx                0/2     Init:0/1   0       ← (repeats until MariaDB is ready)
database-xxx                0/2     PodInitializing    ← Init container finished; app containers start
database-xxx                1/2     Running            ← MariaDB is running; phpMyAdmin starts
database-xxx                2/2     Running            ← Both containers are running
```

**Terminal 2 – show the logs of the init container:**

```bash
kubectl logs -l app=database -n k8s-training -c wait-for-mariadb
```

Expected output:

```
Waiting for MariaDB on localhost:3306 ...
MariaDB is not ready yet -- waiting 2s ...
MariaDB is not ready yet -- waiting 2s ...
MariaDB is ready!
```

### Summary init containers

| Aspect | Behaviour |
|--------|-----------|
| **Order** | Init containers run **sequentially** before all app containers |
| **Lifetime** | Once until the successful exit code 0 |
| **On failure** | The Pod does not start app containers – stays in `Init:` status |
| **Restart** | Init containers do **not** restart automatically (no crash loop) |
| **Typical use** | Waiting for dependencies, schema migrations, preparing files |
| **Image** | Any image – need not match the app image |
