## ConfigMaps

Bisher stehen Konfigurationswerte wie `PUID`, `PGID`, `TZ` und das Code-Server-Passwort direkt
in den Deployment-YAMLs aus Tag 1. Das ist wartbar, solange es nur ein Deployment betrifft --
aber spätestens beim zweiten Deployment wiederholen sich die Werte.

Eine **ConfigMap** ist ein Kubernetes-Objekt, das Konfigurationsdaten als Key-Value-Paare
speichert und an Container weitergibt -- entweder als **Umgebungsvariable** oder als **Datei**
(über ein Volume).

### Beispiel: Code-Server-Workspace auslagern

Der Code-Server aus Tag 1 hat die Umgebungsvariable `DEFAULT_WORKSPACE` hart im YAML stehen:

```yaml
env:
  - name: DEFAULT_WORKSPACE
    value: "/config/workspace"
```

Das lagern wir jetzt in eine ConfigMap aus.

**1. ConfigMap erstellen**

Datei `code-server-config-map.yaml`:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: code-server-config
  namespace: k8s-training
data:
  DEFAULT_WORKSPACE: "/config/workspace"
  PUID: "1000"
  PGID: "1000"
  TZ: "Europe/Berlin"
```

```bash
kubectl apply -f code-server-config-map.yaml
```

**2. ConfigMap im Deployment verwenden**

Statt einzelner `env`-Einträge binden wir die gesamte ConfigMap mit `envFrom` ein:

```yaml
envFrom:
  - configMapRef:
      name: code-server-config
```

Das Deployment sieht dann so aus (Auszug):

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: code-server
  namespace: k8s-training
spec:
  # ... selector, template etc. ...
  template:
    spec:
      containers:
        - name: code-server
          image: lscr.io/linuxserver/code-server:latest
          ports:
            - containerPort: 8443
          envFrom:                          # ConfigMap als Umgebungsvariablen
            - configMapRef:
                name: code-server-config
          env:
            - name: PASSWORD                # Secret bleibt vorerst hart codiert
              value: "training2024"
```

```bash
kubectl apply -f code-server-deployment.yaml
```

**Wichtig:** `envFrom` importiert **alle** Keys der ConfigMap als Umgebungsvariablen.
Der Key `DEFAULT_WORKSPACE` wird zur Variable `DEFAULT_WORKSPACE` mit Wert `/config/workspace`.

### ConfigMap als Volume (Datei)

Neben Umgebungsvariablen kann eine ConfigMap auch als **Volume** in den Container eingebunden
werden. Jeder Key wird dann zu einer eigenen Datei. Das ist praktisch für Konfigurationsdateien
wie `nginx.conf`, `prometheus.yml` oder `vector.toml`.

```yaml
volumes:
  - name: config-volume
    configMap:
      name: app-config
```

Im Container erscheint dann z. B. die Datei `/etc/config/DEFAULT_WORKSPACE` mit dem Inhalt
`/config/workspace`. Dieses Pattern werden wir in der Sidecar-Übung direkt anwenden.

**Zusammenfassung**

| Methode | Beschreibung | Einsatz |
|---------|-------------|---------|
| `envFrom` + `configMapRef` | Alle Keys als Umgebungsvariablen | Mehrere Deployments teilen sich Konfiguration |
| `valueFrom.configMapKeyRef` | Einzelner Key als Umgebungsvariable | Selektives Einbinden |
| Volume-Mount | ConfigMap als Dateien im Dateisystem | Konfigurationsdateien für Tools (Vector, nginx, ...) |

**Merke:** ConfigMaps sind für **nicht-sensitive** Daten. Für Passwörter, Tokens und
Zertifikate gibt es Secrets.

### Secret: Code-Server-Passwort auslagern

Das Code-Server-Passwort steht noch hart codiert im Deployment. Das lagern wir jetzt in ein
[Secret](/docs/kubernetes-basis/90-glossar#secret) aus.

**1. Secret erstellen**

Datei `code-server-secret.yaml`:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: code-server-secret
  namespace: k8s-training
type: Opaque
stringData:
  PASSWORD: "trainingk8s"
```
<br/>
```bash
kubectl apply -f code-server-secret.yaml
```

**2. Secret prüfen**

```bash
kubectl get secret code-server-secret -n k8s-training -o yaml
```

Die Ausgabe zeigt `PASSWORD: dHJhaW5pbmcya3M=` – das ist Base64-kodiert, nicht verschlüsselt:

```bash
echo "dHJhaW5pbmcya3M=" | base64 -d
# Ausgabe: trainingk8s
```

```powershell
[System.Text.Encoding]::UTF8.GetString([System.Convert]::FromBase64String("dHJhaW5pbmcya3M="))
# Ausgabe: trainingk8s
```
<br/>

<Notice type="info">

**💡 Die häufigste Frage: "Warum ist Base64 dann keine Sicherheitskatastrophe?"**

Base64 ist keine Verschlüsselung, sondern nur eine Kodierung – wie eine andere Schreibweise.
Das ist Absicht: Secrets müssen maschinenlesbar sein und dürfen keine Sonderzeichen enthalten,
die YAML oder Env-Variablen kaputtmachen.

Die echte Sicherheit liegt nicht in der Kodierung, sondern in diesen Mechanismen:

| Mechanismus | Wirkung |
|-------------|---------|
| **RBAC** | Nur berechtigte Personen/Systeme dürfen `kubectl get secret` ausführen |
| **Encryption at Rest** | Der Cluster verschlüsselt Secrets auf der Festplatte (seit Kubernetes 1.13+ standardmäßig aktiviert) |
| **Encryption in Transit** | Die API-Kommunikation läuft über TLS – niemand kann den Traffic mitlesen |
| **Kein Git** | Secrets werden nicht in YAML-Dateien committed, sondern nur im Cluster gespeichert |
| **stringData** | Du gibst das Passwort im Klartext an – nur Kubernetes selbst kodiert es nach Base64 |

**Zusammengefasst:** Der Base64-"Schutz" ist eine Kodierung für den Datentransport, kein
Sicherheitsfeature. Die Absicherung kommt von RBAC, TLS und Verschlüsselung im Cluster.
Wer `kubectl get secret` ausführen darf, kommt auch an die Werte – und genau das muss
über Berechtigungen gesteuert werden.

</Notice>
<br/>

**3. Secret im Deployment verwenden**

Statt `value: "training2024"` referenzieren wir den Wert aus dem Secret:

```yaml
env:
  - name: PASSWORD
    valueFrom:
      secretKeyRef:
        name: code-server-secret
        key: PASSWORD
```

```bash
kubectl apply -f code-server-deployment.yaml
```

**Wichtig:** Das Secret muss **im gleichen Namespace** wie der Pod erstellt werden. Bei
Namespace-Abweichung (z. B. `k8s-prod` statt `k8s-training`) entsprechend anpassen.

## Pods und Container-Typen

Bisher haben wir Pods nur als einfache Container-Wrapper kennengelernt. Tatsächlich können Pods
mehrere Container enthalten, die denselben Netzwerk-Namespace und dieselben Volumes teilen. Dieses
Konzept wird genutzt, um eng gekoppelte Prozesse gemeinsam zu deployen und zu verwalten.

### Container-Typen

| Typ                   | Zweck                                   | Lebensdauer                   |
| --------------------- | --------------------------------------- | ----------------------------- |
| [**App-Container**](/docs/kubernetes-basis/90-glossar#app-container)     | Hauptanwendung                          | Läuft dauerhaft               |
| [**Init-Container**](/docs/kubernetes-basis/90-glossar#init-container)    | Initialisierung vor dem App-Start       | Läuft einmalig bis Abschluss  |
| [**Sidecar-Container**](/docs/kubernetes-basis/90-glossar#sidecar-container) | Unterstützende Dienste (Logging, Proxy) | Läuft dauerhaft neben der App |

**Regel:** Mehrere Container im selben Pod nur, wenn sie eng gekoppelt sind. Ansonsten separate Pods
verwenden. Die Container EINER App sind hier NICHT eng gekoppelt, sondern nur lose verbunden über Services und Ingress. Daher deployen wir sie in separaten Pods.

<Image src={knba20002} alt="Multiple container pro Pod * Erstellt mit Microsoft Copilot" />


### Init-Container

Init-Container laufen sequenziell, bevor die App-Container starten. Jeder muss erfolgreich
abschließen. Dies dient nur zur Voranschau, dieses Konzept werden wir später verwenden. 

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app-mit-init
  namespace: k8s-training
spec:
  initContainers:
    - name: wait-for-db
      image: busybox:1.28
      command:
        - sh
        - -c
        - 'until nslookup my-database.k8s-training.svc.cluster.local; do echo "Warte auf DB...";
          sleep 2; done'
  containers:
    - name: app
      image: nginx:1.27
      ports:
        - containerPort: 80
```

Typische Anwendungsfälle:

- Warten auf eine Datenbank oder einen externen Service
- Konfigurationsdateien vorbereiten
- Schema-Migrationen ausführen

### Sidecar-Container

Sidecar-Container laufen dauerhaft neben der Hauptanwendung und teilen sich Netzwerk und Volumes.
Typische Einsatzmuster:

| Pattern | Beschreibung | Beispiel |
|---------|-------------|----------|
| **Log-Shipper** | Liest Logs der App und sendet sie an eine zentrale Logging-Plattform | Vector, Fluent Bit, Promtail |
| **Reverse-Proxy** | Übernimmt SSL-Terminierung, Auth oder Raten-Limiting für die App | nginx, Envoy, oauth2-proxy |
| **Metrics-Exporter** | Sammelt Metriken der App und exponiert sie für Prometheus | nginx-prometheus-exporter, node-exporter |
| **Service Mesh** | Übernimmt gesamte Netzwerk-Kommunikation (TLS, Tracing, Retries) | Envoy (Istio), Linkerd-proxy |

#### Übung: Chromium mit Vector als Sidecar

> **Vertiefung:** Im ConfigMap-Kapitel oben hast du gelernt, wie ConfigMaps als Umgebungsvariablen
> funktionieren (`envFrom`). Hier kommt die zweite Variante: **ConfigMap als Volume** -- der Key
> `vector.toml` wird zur Datei `/etc/vector/vector.toml` im Container.

In dieser Übung statten wir **unser Chromium** mit einem Vector-Sidecar aus.
Chromium (linuxserver.io) schreibt Logs nach `/config/log/` -- der Sidecar liest diese Logs
und gibt sie als JSON auf der Konsole aus. Beide Container teilen sich ein `emptyDir`-Volume.

<br/>

**1. ConfigMap für Vector-Konfiguration erstellen**

Datei `vector-config.yaml`:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: vector-config
  namespace: k8s-training
data:
  vector.toml: |
    [sources.chromium_logs]
      type = "file"
      include = ["/config/log/*.log"]
      read_from = "beginning"

    [sinks.console]
      type = "console"
      inputs = ["chromium_logs"]
      encoding.codec = "json"
```

```bash
kubectl apply -f vector-config.yaml
```
<br/>

**2. Chromium-Deployment um Sidecar erweitern**

Das bestehende Deployment aus Tag 1 (`chromium-deployment.yaml`) bekommt einen zweiten Container
und ein gemeinsames Volume. Die Änderungen sind mit `# NEU` markiert:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: chromium
  namespace: k8s-training
  labels:
    app: chromium
spec:
  replicas: 1
  selector:
    matchLabels:
      app: chromium
  template:
    metadata:
      labels:
        app: chromium
    spec:
      containers:
        - name: chromium
          image: lscr.io/linuxserver/chromium:latest
          ports:
            - containerPort: 3000
            - containerPort: 3001
          env:
            - name: PUID
              value: "1000"
            - name: PGID
              value: "1000"
            - name: TZ
              value: "Europe/Berlin"
          volumeMounts:
            - name: shm
              mountPath: /dev/shm
            - name: chromium-logs          # NEU: gemeinsames Log-Volume
              mountPath: /config/log
        - name: vector                     # NEU: Sidecar-Container
          image: timberio/vector:0.42.0-alpine
          command:
            - vector
            - --config
            - /etc/vector/vector.toml
          volumeMounts:
            - name: chromium-logs          # NEU: gleiches Volume wie Chromium
              mountPath: /config/log
            - name: vector-config
              mountPath: /etc/vector
      volumes:
        - name: shm
          emptyDir:
            medium: Memory
            sizeLimit: 1Gi
        - name: chromium-logs              # NEU: shared emptyDir für Logs
          emptyDir: {}
        - name: vector-config              # NEU: ConfigMap als Volume
          configMap:
            name: vector-config
```
<br/>
```bash
kubectl apply -f chromium-deployment.yaml
```
<br/>

**3. Funktion prüfen**

```bash
# Warten, bis der neue Pod läuft
kubectl get pods -l app=chromium -w

# Logs des Sidecars anzeigen
kubectl logs -l app=chromium -c vector

# Logs von Chromium anzeigen (Vergleich)
kubectl logs -l app=chromium -c chromium

# Chromium im Browser öffnen und ein paar Seiten besuchen,
# dann erneut Sidecar-Logs prüfen:
kubectl logs -l app=chromium -c vector --tail=10
```
<br/>

**4. Was passiert hier?**

- Chromium sollte die Logs nach `/config/log/` (z. B. `chromium.log`, `Xorg.log`) schreiben
- Der Sidecar (`vector`) liest **dieselben Dateien** über das gemeinsame `emptyDir`-Volume
- Vector parst die Logs und gibt sie als JSON auf der Konsole aus
- **Wichtig:** Beide Container laufen im selben Pod -- teilen sich Netzwerk (`localhost`) und Volume
- Der Sidecar wurde **nachträglich** in ein bestehendes Deployment eingefügt -- Kubernetes startet
  den Pod automatisch neu mit beiden Containern

<br/>

**5. Typische Beobachtung: Vector läuft, aber keine Logs?**

```bash
kubectl logs -l app=chromium -c vector
```

Du siehst, dass Vector startet und der Healthcheck erfolgreich ist:

```
INFO vector::app: Vector has started.
INFO vector::topology::builder: Healthcheck passed.
INFO vector::sources::file: Starting file server. include=["/config/log/*.log"] exclude=[]
```

Aber es kommen **keine JSON-Logs**. Das ist **kein** Fehler in deiner Konfiguration – es liegt
daran, wie das Chromium-Image seine Logs behandelt.

**Warum?** Das linuxserver/chromium-Image startet Chromium über das Script
`/usr/bin/wrapped-chromium`. Die letzte Zeile dort leitet **alle** Ausgaben nach `/dev/null` um:

```bash
${BIN} \
  --no-sandbox \
  --password-store=basic \
  --simulate-outdated-no-au='Tue, 31 Dec 2099 23:59:59 GMT' \
  --start-maximized \
  --test-type \
  --user-data-dir \
  ${WAYLAND} \
   "$@" > /dev/null 2>&1
```

Chromium schreibt also **nie** Logs in Dateien – weder nach `/config/log/` noch sonst wohin.
Die Container-Logs, die du mit `kubectl logs -c chromium` siehst, stammen von s6-overlay,
nicht von Chromium selbst.

**Lösung:** Wir ersetzen das `wrapped-chromium`-Script durch eine eigene Version, die Logs
sowohl nach `/config/log/chromium.log` als auch nach stdout schreibt. Dazu mounten wir das
angepasste Script per ConfigMap mit `subPath` über das originale Script.
<br/>

**6. Logging aktivieren: Custom Startup-Script**

Datei `chromium-logging-configmap.yaml`:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: chromium-logging
  namespace: k8s-training
data:
  wrapped-chromium: |
    #!/bin/bash

    BIN=/usr/bin/chromium
    LOGFILE=/config/log/chromium.log

    # Cleanup
    if ! pgrep chromium > /dev/null;then
      rm -f $HOME/.config/chromium/Singleton*
    fi

    # Wayland check
    WAYLAND=""
    if ls -l /dev/dri/* > /dev/null 2>&1; then
      if pgrep labwc > /dev/null 2>&1; then
        WAYLAND="--ozone-platform=wayland"
      fi
    fi

    # Chromium starten mit Logs in Datei UND stdout
    ${BIN} \
      --no-sandbox \
      --password-store=basic \
      --simulate-outdated-no-au='Tue, 31 Dec 2099 23:59:59 GMT' \
      --start-maximized \
      --test-type \
      --user-data-dir \
      ${WAYLAND} \
       "$@" > >(tee -a ${LOGFILE}) 2>&1
```

```bash
kubectl apply -f chromium-logging-configmap.yaml
```
<br/>

**7. Deployment aktualisieren**

Das Chromium-Deployment bekommt einen zusätzlichen Volume-Mount, der das ConfigMap-Script
über das originale `wrapped-chromium` legt. Wichtig: `subPath` mountet nur die einzelne Datei,
ohne den Rest des Verzeichnisses zu überdecken. `defaultMode: 0755` macht das Script ausführbar.

Datei `chromium-deployment-sidecar-wrapped.yaml`

```yaml
apiVersion: apps/v1
kind: Deployment
      ...
      volumes:
        - name: shm
          ...
        - name: chromium-logging-script         # NEU: ConfigMap mit Script
          configMap:
            name: chromium-logging
            defaultMode: 0755
```

```bash
kubectl apply -f chromium-deployment.yaml
```
<br/>

**8. Funktion prüfen**

```bash
# Warten, bis der neue Pod läuft
kubectl get pods -l app=chromium -w

# Logs des Sidecars anzeigen – jetzt sollten JSON-Logs kommen!
kubectl logs -l app=chromium -c vector --tail=10

# Prüfen, ob die Log-Datei im Container existiert
kubectl exec -c chromium deploy/chromium -- ls -la /config/log/

# Chromium-Logs live verfolgen
kubectl logs -l app=chromium -c vector -f
```

**Erwartete Ausgabe von Vector:**

```json
{"file":"/config/log/chromium.log","host":"chromium-...","message":"[381:411:0719/...:ERROR:...] Registration response error message: DEPRECATED_ENDPOINT","source_type":"file","timestamp":"2026-07-19T..."}
{"file":"/config/log/chromium.log","host":"chromium-...","message":"DevTools listening on ws://...","source_type":"file","timestamp":"2026-07-19T..."}
```

Jetzt streamt Vector die Chromium-Logs als strukturiertes JSON – bereit für die
Weiterverarbeitung durch Elasticsearch, Loki oder eine andere Logging-Plattform.

**Hinweis:** Die Logs enthalten jetzt auch Chromium-Internals wie `ERROR`, `WARNING` und
`INFO`-Meldungen. Das ist normal – Chromium loggt viele interne Vorgänge (GPU, Netzwerk,
Extensions). In Produktion könnte man mit Vector-Filtern (`[transforms]`) bestimmte
Log-Level oder Komponenten herausfiltern.

#### Produktiv-Alternativen

## Requests & Limits


Stell dir vor, im Logistikzentrum arbeiten mehrere Abteilungen nebeneinander.
Jede Abteilung hat einen bestimmten Platzbedarf und bestimmte Maschinen.

- **Ohne Absprache** würde eine Abteilung einfach den ganzen Lagerplatz blockieren,
  die Gabelstapler dauerhaft belegen und den Strom für alle anderen verbrauchen.
  Chromium ist so eine Abteilung – ein Speicherfresser, der sich ohne Limits
  die ganze Node vollsaugt, bis andere Pods verhungern.

- **`requests`** ist die **Mindestgarantie**: "Diese Abteilung bekommt mindestens
  3 Regalreihen und 1 Gabelstapler – das darf ihr keiner wegnehmen." Der
  Lagerleiter (Scheduler) platziert die Abteilung nur, wenn genug Platz frei ist.

- **`limits`** ist die **Obergrenze**: "Mehr als 6 Regalreihen und 2 Gabelstapler
  darf diese Abteilung nicht nutzen – auch wenn noch Platz wäre." So bleibt
  für alle anderen genug übrig.

**Zusammengefasst:** Ohne `requests` kann eine Abteilung verhungern, weil eine
andere alles blockiert. Ohne `limits` kann eine Abteilung das ganze Lager lahmlegen.
Requests und Limits sorgen für **Fairness und Stabilität** im Logistikzentrum.

- **`requests`** – Mindestgarantie. Der Scheduler platziert den Pod nur auf einer Node,
  die diese Menge garantiert frei hat.
- **`limits`** – Obergrenze. CPU wird bei Überschreitung gedrosselt, bei Memory gibt's
  einen OOM-Kill.

> **OOM = Out Of Memory.** Überschreitet ein Container sein `limits.memory`, schickt der
> Linux-Kernel das Signal `SIGKILL` (Exit Code 137). Der Container wird sofort beendet und
> vom Deployment automatisch neu gestartet. Passiert das immer wieder, landet er im
> `CrashLoopBackOff`.

Der Abstand zwischen requests und limits bestimmt die [QoS-Klasse](#qos-klassen) und damit,
wie prioritär der Pod behandelt wird, wenn die Node unter Druck gerät.

| Konzept      | Beschreibung                                                                     |
| ------------ | -------------------------------------------------------------------------------- |
| [**requests**](/docs/kubernetes-basis/90-glossar#resource-limits) | Mindestgarantie -- Scheduler platziert Pod nur auf Nodes mit genügend Ressourcen |
| [**limits**](/docs/kubernetes-basis/90-glossar#resource-limits)   | Obergrenze -- CPU wird gedrosselt, bei Speicherüberschreitung OOM-Kill           |

**CPU-Einheiten:** `1` = 1 Kern, `500m` = 0,5 Kerne, `250m` = 0,25 Kerne.

<Notice type="info">

**💡 Das `m` steht für "Milli"** – ein Tausendstel eines Kerns. `1000m` = 1 voller Kern.
Ein Container kann maximal so viele Millicores bekommen, wie die Node an Kernen hat.
Werte über `1000m` (Bsp. `2000m`) ergeben nur Sinn auf einer Node mit mindestens 2 Kernen.

</Notice>

**Speicher-Einheiten:** `128Mi` = 128 Mebibyte, `1Gi` = 1 Gibibyte.

<Notice type="info">

**💡 Das `Mi` und `Gi` steht für "Mebi" und "Gibi"** – binäre Einheiten (Basis 1024).
`1 Mi` = 1024 × 1024 Byte = 1.048.576 Byte (im Gegensatz zu `1 MB` = 1.000.000 Byte).
Kubernetes rechnet immer binär. Merkregel:

- `i` = binär (Mi, Gi, Ti) – das ist der Kubernetes-Standard
- Nur Buchstabe = dezimal (M, G, T) – wird von Kubernetes auch akzeptiert, aber binär interpretiert

| Einheit | Bytes | Gerundet |
|---------|-------|----------|
| `128Mi` | 134.217.728 | ~128 MB |
| `256Mi` | 268.435.456 | ~256 MB |
| `512Mi` | 536.870.912 | ~512 MB |
| `1Gi`   | 1.073.741.824 | ~1 GB |
| `5Gi`   | 5.368.709.120 | ~5 GB |

</Notice>

### QoS-Klassen

**Analogie zum Logistikzentrum:**

Die QoS-Klasse sagt: "Wie wichtig ist diese Abteilung, wenn der Platz knapp wird?"

- **BestEffort** – eine Abteilung, die nie angemeldet hat, wie viel Platz sie braucht.
  Wenn das Lager voll wird, fliegt sie als Erste raus.
- **Burstable** – eine Abteilung, die 3 Regalreihen reserviert hat, aber bis zu 6 nutzen
  darf. Solange Platz ist, bekommt sie die Extrereihen. Wird es eng, muss sie auf ihre
  reservierten 3 zurück.
- **Guaranteed** – eine Abteilung, die genau 3 Regalreihen reserviert und auch nicht mehr
  nutzen darf. Sie ist planbar und wird als Letzte angerührt.

| [QoS-Klasse](/docs/kubernetes-basis/90-glossar#qos-klassen)     | Bedingung                               | Eviction-Priorität           | Analogie |
| -------------- | --------------------------------------- | ---------------------------- | -------- |
| **Guaranteed** | requests == limits (für CPU und Memory) | Niedrigste (zuletzt evicted) | Feste Zusage: genau 3 Regalreihen |
| **Burstable**  | requests < limits                       | Mittel                       | Flexibel: 3 reserviert, bis zu 6 |
| **BestEffort** | Keine requests/limits gesetzt           | Höchste (zuerst evicted)     | Keine Reservierung, wird zuerst geräumt |

**Merke:** Je genauer du requests und limits kennst, desto planbarer ist dein Pod.
`Guaranteed` ist der Königsweg für produktive Workloads – der Pod wird nur evicted,
wenn es absolut keinen anderen Ausweg mehr gibt.

### Resource Limits

Das Deployment von Chromium läuft noch ohne Resource-Angaben. Das ändern wir jetzt.

**Beachte:** Die QoS-Klasse wird nicht direkt konfiguriert – sie ergibt sich automatisch
aus dem Verhältnis von `requests` und `limits`:

| Konstellation | QoS-Klasse |
|---|---|
| `requests` < `limits` | **Burstable** |
| `requests` == `limits` | **Guaranteed** |
| Keine `resources` | **BestEffort** |

Datei `chromium-deployment-res.yaml` -- ergänze den `resources`-Block im Container.
Der Rest des Deployments bleibt:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: chromium
  namespace: k8s-training    # ⬅️ Namespace ggf. anpassen
  labels:
    app: chromium
spec:
  # ... replicas, selector, template (unverändert) ...
  template:
    spec:
      containers:
        - name: chromium
          # ... image, ports, env, volumeMounts (unverändert) ...
          resources:                          # ⬅️ NEU
            requests:
              cpu: "250m"
              memory: "512Mi"
            limits:
              cpu: "1000m"
              memory: "1Gi"
```
<br/>

```bash
kubectl apply -f chromium-deployment-res.yaml
```

### LimitRange

Eine [LimitRange](/docs/kubernetes-basis/90-glossar#limitrange) setzt Standardwerte für alle Container, die keine eigenen Resources angeben.

<Notice type="warning">

**⚠️ Achtung:** `LimitRange` ist eine administrative Ressource und benötigt **Cluster-Admin-Rechte**.
In vielen Trainings-Clustern hast du nur Readonly-Zugriff – dann schlägt `kubectl apply` mit

</Notice>

Datei `limitrange.yaml`:

```yaml

metadata:
  name: standard-limits
  namespace: k8s-training
spec:
  limits:
    - default:
        cpu: "500m"
        memory: "256Mi"
      defaultRequest:
        cpu: "100m"
        memory: "64Mi"
      max:
        cpu: "2"
        memory: "2Gi"
      min:
        cpu: "50m"
        memory: "32Mi"
      type: Container
```
<br/>
```bash
kubectl apply -f limitrange.yaml
```

```powershell
kubectl apply -f limitrange.yaml
```

## Health Checks

Kubernetes weiß nicht automatisch, ob eine Anwendung wirklich funktioniert -- nur ob ein Container
läuft. Health Checks (Probes) geben Kubernetes diese Intelligenz: Sie prüfen regelmäßig den Zustand
eines Containers und lösen automatische Aktionen aus, wenn etwas nicht stimmt.

### Probe-Typen

| Probe               | Frage                                 | Aktion bei Fehlschlag                      |
| ------------------- | ------------------------------------- | ------------------------------------------ |
| [**Liveness Probe**](/docs/kubernetes-basis/90-glossar#liveness-probe)  | Läuft die Anwendung noch?             | Container wird neu gestartet               |
| [**Readiness Probe**](/docs/kubernetes-basis/90-glossar#readiness-probe) | Kann die Anwendung Traffic empfangen? | Pod wird aus Service-Endpoints entfernt    |
| [**Startup Probe**](/docs/kubernetes-basis/90-glossar#startup-probe)   | Ist die Anwendung fertig gestartet?   | Liveness/Readiness pausiert bis Startup OK |

### Probe-Mechanismen

| Mechanismus | Beschreibung                                   |
| ----------- | ---------------------------------------------- |
| `httpGet`   | HTTP GET an Pfad+Port; Status 200-399 = gesund |
| `exec`      | Befehl im Container; Exit-Code 0 = gesund      |
| `tcpSocket` | Prüft ob TCP-Port offen ist                    |

### Parameter

| Parameter             | Beschreibung                 | Standard |
| --------------------- | ---------------------------- | -------- |
| `initialDelaySeconds` | Wartezeit vor erster Prüfung | 0        |
| `periodSeconds`       | Intervall zwischen Prüfungen | 10       |
| `timeoutSeconds`      | Timeout pro Prüfung          | 1        |
| `successThreshold`    | Erfolge bis "gesund"         | 1        |
| `failureThreshold`    | Fehlschläge bis "ungesund"   | 3        |

### Warum Linuxserver.io-Images so robust sind

Die Images von Linuxserver.io verwenden **s6-overlay** als Init-System. Das ist kein einfacher
Prozess-Starter, sondern ein vollwertiger Service-Manager — vergleichbar mit einem Mini-Systemd.
s6-overlay überwacht alle gestarteten Prozesse und startet sie **automatisch neu**, falls sie
abstürzen. Das hat weitreichende Folgen für Liveness Probes:

| Eigenschaft | Effekt |
|---|---|
| **Auto-Restart** | Stirbt Chromium, startet s6 es sofort neu — oft bevor Kubernetes die Liveness Probe auslöst |
| **PID 1** | s6 läuft als PID 1 und fängt Zombie-Prozesse, verhindert孤儿-Prozesse |
| **Service-Dependencies** | Dienste starten in der richtigen Reihenfolge (z. B. Chromium erst nach X11/Wayland) |
| **Log-Redirect** | s6 leitet Logs aller Dienste nach stdout — deshalb siehst du in `kubectl logs` nur s6-Meldungen, nicht Chromium selbst |

**Konsequenz für Liveness Probes:** Bei Linuxserver-Images ist eine Liveness Probe oft **wirkungslos**
für den Auto-Restart-Fall — s6 ist schneller. Die Probe greift erst, wenn der gesamte Container
hängt (Prozess lebt, aber antwortet nicht). Das ist kein Fehler, sondern gewollte Robustheit:
Linuxserver-Images sind für den Heimgebrauch konzipiert, wo ein Container möglichst nie sterben soll.

## Probes anwenden

Jetzt konfigurieren wir Probes für unsere beiden Anwendungen. Chromium und Code-Server haben
unterschiedliche Startzeiten -- Chromium ist speicher- und renderingintensiv und braucht beim Start
deutlich länger als Code-Server. Die Probe-Konfiguration muss das berücksichtigen, sonst markiert
Kubernetes neue Container zu früh als "ungesund" und startet sie endlos neu. Wir erweitern die
bestehenden YAML-Manifeste um `startupProbe`, `livenessProbe` und `readinessProbe`.

### Chromium Probes

Datei `chromium-deployment.yaml` erweitern (Resources + Probes):

```yaml
apiVersion: apps/v1
    ...
    spec:
      containers:
        - name: chromium
          ...
          startupProbe:
            httpGet:
              path: /
              port: 3000
            failureThreshold: 30
            periodSeconds: 10
          livenessProbe:
            httpGet:
              path: /
              port: 3000
            periodSeconds: 15
            failureThreshold: 3
          readinessProbe:
            httpGet:
              path: /
              port: 3000
            periodSeconds: 5
            failureThreshold: 1
```
<br/>
- StartupProbe (failureThreshold: 30, periodSeconds: 10) — Chromium braucht bis zu 5 Minuten zum Starten. Die StartupProbe sagt: "Warte ruhig, solange die noch läuft, keine Panik." Solange die StartupProbe läuft, werden Liveness und Readiness ignoriert.
- ReadinessProbe (failureThreshold: 1, periodSeconds: 5) — Chromium ist gestartet, aber der Browser hängt gerade (z. B. eine Seite lädt ewig). Die ReadinessProbe schlägt fehl → der Pod fliegt aus den Endpoints → kein Traffic mehr → Chromium kann sich erholen. Der Pod stirbt nicht, er kriegt nur kurz keinen Traffic.
- LivenessProbe (failureThreshold: 3, periodSeconds: 15) — Chromium ist abgestürzt (Prozess tot, Port antwortet nicht). Nach 3 Fehlschlägen = 45 Sekunden sagt Kubernetes: "Der ist tot" und startet den Container neu.
<br/>
```bash
kubectl apply -f chromium-deployment.yaml
```

### Übung: Readiness Probe manipulieren

In dieser Übung siehst du live, wie die Readiness Probe den Traffic steuert. Du änderst den Port
in der `readinessProbe` auf einen nicht existierenden Port — der Pod wird nicht Ready und
verschwindet aus den Endpoints. Der alte Pod läuft weiter und bedient den Traffic.

1. **Startzustand prüfen** — Ein Pod läuft sauber (`2/2` Ready):

```bash
kubectl get pods -n k8s-training
kubectl get endpointslices -n k8s-training -o wide
```

2. **Falschen Port eintragen** — Ändere in `chromium-deployment.yaml` den Port der
   `readinessProbe` von `3000` auf einen nicht existierenden Port, z. B. `3005`:

```yaml
          readinessProbe:
            httpGet:
              path: /
              port: 3005   # ← falsch! Port 3005 existiert nicht
            periodSeconds: 5
            failureThreshold: 1
```

3. **Deployen und beobachten**:

```bash
kubectl apply -f chromium-deployment.yaml
kubectl get pods -n k8s-training -w
```

Du siehst jetzt **zwei Pods**:
- Der **alte Pod** (`2/2` Ready) — läuft weiter und bedient den Traffic
- Der **neue Pod** (`1/2` Ready) — Chromium ist nicht Ready, weil die Probe auf Port 3005
  fehlschlägt. Der Vector-Container läuft trotzdem (daher `1/2`).

4. **Endpoints prüfen** — Der neue Pod taucht **nicht** in den Endpoints auf:

```bash
kubectl get endpointslices -n k8s-training -o wide
```

Nur die IP des alten Pods ist eingetragen. Der neue Pod bekommt keinen Traffic.

5. **Port korrigieren** — Setze den Port in der `readinessProbe` zurück auf `3000` und deploye
   erneut:

```bash
kubectl apply -f chromium-deployment.yaml
kubectl get pods -n k8s-training -w
```

Der alte Pod wird durch den neuen ersetzt, der jetzt `2/2` Ready ist. Der EndpointSlice zeigt
nur noch die IP des neuen Pods.

6. **Alte ReplicaSets aufräumen** — Nach der Übung sind oft mehrere ReplicaSets übrig, die
   noch die fehlerhafte Konfiguration enthalten. Sie haben `DESIRED: 1` und erstellen immer
   wieder neue Pods mit der kaputten Probe.

   **Was ist ein ReplicaSet?** Es ist die Schicht zwischen Deployment und Pod. Das Deployment
   erstellt ein neues ReplicaSet für jede Änderung am Pod-Template (Bsp. neues Image). Das
   ReplicaSet sorgt dafür, dass immer die gewünschte Anzahl Pods mit einer bestimmten
   Konfiguration läuft. Alte ReplicaSets bleiben mit 0 Replicas erhalten – sie ermöglichen
   Rollbacks, indem das Deployment einfach das vorherige ReplicaSet wieder hochskaliert.

   Prüfe, ob es solche Geister-ReplicaSets gibt:

```bash
kubectl get replicasets -l app=chromium -n k8s-training
```

Suche nach Einträgen mit `DESIRED: 1`, die nicht zum aktuellen Pod gehören. Diese ReplicaSets
kannst du entweder auf 0 skalieren oder ganz löschen:

```bash
kubectl scale replicaset <name-des-alten-rs> --replicas=0 -n k8s-training
# oder
kubectl delete replicaset <name-des-alten-rs> -n k8s-training
```

Danach sollte nur noch ein Pod mit `2/2` Ready laufen.

## Deploy-Strategien

Wie Kubernetes alte Pods durch neue ersetzt, ist keine Kleinigkeit -- falsch konfiguriert entstehen
Ausfallzeiten oder Datenkonflikte. Kubernetes bietet zwei Strategien, zwischen denen du je nach
Anwendungstyp wählen kannst.

### Vergleich

| Strategie         | Verhalten                                    | Ausfallzeit | Einsatz                                               |
| ----------------- | -------------------------------------------- | ----------- | ----------------------------------------------------- |
| [**RollingUpdate**](/docs/kubernetes-basis/90-glossar#rollingupdate) | Pods werden schrittweise ersetzt             | Keine       | Standard, Produktion                                  |
| **Recreate**      | Alle alten Pods beendet, dann neue gestartet | Kurz        | Wenn alte + neue Version nicht parallel laufen können |

### Konfiguration

```yaml
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1 # Wie viele zusätzliche Pods während des Updates erlaubt
      maxUnavailable: 0 # Wie viele Pods gleichzeitig fehlen dürfen
```

- `maxSurge: 1` -- während des Updates darf 1 Pod mehr als `replicas` laufen
- `maxUnavailable: 0` -- es darf kein Pod fehlen (kein Traffic-Verlust)


Mit der konfigurierten RollingUpdate-Strategie führen wir jetzt ein echtes Update durch -- und
lernen, im Fehlerfall sofort zurückzurollen. Als Beispiel ändern wir das Chromium-Image auf
eine andere Version und beobachten den Prozess live.

### Image-Update

```bash
kubectl set image deployment/chromium chromium=lscr.io/linuxserver/chromium:version-11e602ae -n k8s-training
```

### Rollout-Status

```bash
kubectl rollout status deployment/chromium -n k8s-training
```

### ReplicaSets

```bash
kubectl get replicasets -l app=chromium -n k8s-training
```

Es gibt jetzt zwei ReplicaSets -- das alte (0 Replicas) und das neue (1 Replica). Das alte wird für
Rollbacks aufbewahrt.

### Fehlerfall

Ein fehlerhaftes Image setzen:

```bash
kubectl set image deployment/chromium chromium=lscr.io/linuxserver/chromium:nicht-existent -n k8s-training
```

Beobachten:

```bash
kubectl get pods -l app=chromium -n k8s-training
```

Der neue Pod bleibt in `ImagePullBackOff` hängen. Das alte ReplicaSet hält den bisherigen Pod noch
am Laufen (dank `maxUnavailable: 0`).

### Rollback

```bash
kubectl rollout undo deployment/chromium -n k8s-training
kubectl rollout status deployment/chromium -n k8s-training
```

### Rollout-Historie

```bash
kubectl rollout history deployment/chromium -n k8s-training
```

Zu einer bestimmten Revision zurückrollen:

```bash
kubectl rollout undo deployment/chromium --to-revision=1 -n k8s-training
```

### Skalierung

```bash
# Hochskalieren
kubectl scale deployment/chromium --replicas=3 -n k8s-training
kubectl get pods -l app=chromium -n k8s-training

# Runterskalieren
kubectl scale deployment/chromium --replicas=1 -n k8s-training
kubectl get pods -l app=chromium -n k8s-training
```


## PVs & PVCs

Container-Dateisysteme sind flüchtig -- stirbt ein Pod, sind alle Daten weg. Für Anwendungen
wie MariaDB ist das keine Option. Persistent Volumes (PVs) und Persistent Volume Claims
(PVCs) entkoppeln Storage von der Pod-Lebensdauer.



### Analogie: Das Logistiklager

Stell dir vor, du betreibst ein Logistiklager mit mehreren Hallen (Nodes). Jede Halle hat
viel Platz, aber der ist nicht unbegrenzt.

- **Ohne Persistent Storage** ist jeder Arbeitsauftrag (Pod) ein Einweg-Tisch: Du stellst
  deine Kisten drauf, aber wenn der Auftrag erledigt ist, wird der Tisch weggeworfen –
  mitsamt deiner Kisten. Genau das passiert mit `emptyDir`: Der Pod stirbt, die Daten sind
  weg.

- **Ein PersistentVolume (PV)** ist wie ein **fest installiertes Regal** in der Halle. Es
  steht da, unabhängig von einzelnen Aufträgen. Der Lagerleiter (Admin) hat es aufgebaut,
  oder es wurde automatisch bestellt (dynamische Provisionierung).

- **Ein PersistentVolumeClaim (PVC)** ist der **Lagerzettel**, den ein Mitarbeiter (Pod)
  ausfüllt: "Ich brauche ein Regal mit 1 Meter Fachbreite, das ich alleine nutzen kann
  (`ReadWriteOnce`)." Der Lagerleiter schaut, ob ein passendes Regal (PV) frei ist, und
  weist es dem Mitarbeiter zu.

- **Die StorageClass** ist der **Katalog mit Regaltypen**: "Standard-Regal (Festplatte)",
  "Schnell-Regal (SSD)", "Kühl-Regal (Archive)". Der Mitarbeiter sagt nur "Ich brauche
  ein Standard-Regal" – die StorageClass kümmert sich darum, dass das richtige Regal
  geliefert und aufgebaut wird.

**Zusammengefasst:** PV = das Regal in der Halle. PVC = der Zettel, der das Regal reserviert.
StorageClass = der Katalog, der bestimmt, welches Regal geliefert wird. Der Pod arbeitet
am Regal – und wenn der Pod weg ist, bleibt das Regal stehen.

### Konzepte

| Konzept                         | Beschreibung                                                          |
| ------------------------------- | --------------------------------------------------------------------- |
| [**PersistentVolume (PV)**](/docs/kubernetes-basis/90-glossar#persistentvolume)       | Ein Stück Storage im Cluster, bereitgestellt von Admin oder dynamisch |
| [**PersistentVolumeClaim (PVC)**](/docs/kubernetes-basis/90-glossar#persistentvolumeclaim) | Anforderung eines Pods an Storage (Größe, Zugriffsart)                |
| [**StorageClass**](/docs/kubernetes-basis/90-glossar#storageclass)                | Definiert, wie PVs dynamisch erstellt werden (Provisioner, Parameter) |

### Lifecycle

```
PVC-Anforderung → StorageClass erstellt PV → Pod mountet PVC
```

1. Ein PVC wird erstellt mit gewünschter Größe und Zugriffsart
2. Die StorageClass provisioniert automatisch ein passendes PV
3. Der Pod referenziert den PVC als Volume und mountet ihn

**Erinnerung an Tag 1:** Beim Löschen des Code-Server Pods war die erstellte Datei weg. Das liegt
daran, dass `emptyDir`-Volumes mit dem Pod sterben. PVCs überleben Pod-Neustarts und sogar
Pod-Löschungen.

### Übung: Flüchtigkeit erleben

Bevor wir mit PVCs arbeiten, sollst du selbst spüren, was "flüchtig" bedeutet.

1. **Code-Server im Browser öffnen** und eine beliebige Datei im Workspace erstellen
   (Bsp. `test.txt` mit etwas Inhalt).

2. **Pod neu starten** -- lösche den Pod, das Deployment erstellt automatisch einen neuen:

   ```bash
   kubectl delete pod -l app=code-server -n k8s-training
   ```

3. **Warten**, bis der neue Pod läuft:

   ```bash
   kubectl get pods -l app=code-server -n k8s-training -w
   ```

4. **Code-Server neu laden** -- die Datei ist weg (evt. noch im Editor geöffnet, Browser-Cache). Der Workspace wurde mit `emptyDir`
   gemountet und existiert nicht mehr.

5. **Erkenntnis:** Container-Dateisysteme sind flüchtig. Ohne persistenten Storage
   sind alle Daten nach einem Pod-Neustart verloren.

### Code-Server: PVC (persistent)

Der Code-Server aus Tag 1 verwendet `emptyDir` für `/config` -- das hast du bereits in der
Übung "Flüchtigkeit erleben" oben gesehen. Jetzt rüsten wir ihn auf **PVC** um, damit der
Workspace Pod-Neustarts überlebt.

Dazu brauchen wir zwei Dinge: den PVC und ein aktualisiertes Deployment, das den PVC statt
`emptyDir` verwendet. Der Service bleibt unverändert -- der Code-Server ist weiterhin unter
derselben Adresse erreichbar.

Datei `code-server-pvc.yaml`:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: code-server-config
  namespace: k8s-training
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi
```

Das Deployment aus Tag 1 (`code-server-deployment.yaml`) bekommt nur eine kleine Änderung:
Statt `emptyDir: {}` referenzieren wir den PVC. Der Rest bleibt identisch.

**Alte Version (Tag 1):**

```yaml
      volumes:
        - name: config
          emptyDir: {}
```

**Neue Version mit PVC:**

```yaml
      volumes:
        - name: config
          persistentVolumeClaim:
            claimName: code-server-config
```

```bash
kubectl apply -f code-server-pvc.yaml
kubectl apply -f code-server-deployment-pvc.yaml
```

**Wichtig:** Der Pod wird durch das Update neu gestartet -- aber weil wir vorher noch keinen
PVC hatten, ist der Workspace beim ersten Start leer. Erst ab jetzt bleiben die Daten erhalten.

### Persistenz-Test: Daten überleben den Pod-Neustart

PVC-Status prüfen:

```bash
kubectl get pvc -n k8s-training
```

Der PVC sollte den Status `Bound` haben.

Jetzt der entscheidende Test: Du erstellst eine Datei im Workspace, löschst den Pod und prüfst,
ob sie noch da ist, wenn der neue Pod läuft.

```bash
# Datei im persistenten Volume erstellen
kubectl exec $(kubectl get pod -l app=code-server -n k8s-training -o jsonpath='{.items[0].metadata.name}') -n k8s-training -- touch /config/workspace/test.txt

# Pod löschen (Deployment erstellt neuen)
kubectl delete pod -l app=code-server -n k8s-training

# Warten bis neuer Pod läuft
kubectl get pods -l app=code-server -n k8s-training -w

# Datei prüfen -- sie überlebt!
kubectl exec $(kubectl get pod -l app=code-server -n k8s-training -o jsonpath='{.items[0].metadata.name}') -n k8s-training -- ls /config/workspace/test.txt
```

## 🧪 Vertiefung: Init-Container für MariaDB-Wartezeit (optional)

In der Sidecar-Übung mit Vector hast du gesehen, wie zwei Container parallel starten.
Bei MariaDB + phpMyAdmin ist das anders: phpMyAdmin **braucht** eine laufende MariaDB,
sonst zeigt es nur eine Fehlerseite. Ein Init-Container löst das: Er läuft **vor** den
App-Containern und blockiert so lange, bis MariaDB bereit ist. Erst dann starten
phpMyAdmin (und MariaDB neu – aber die ist ja schon da).

> **Erinnerung:** Init-Container wurden weiter oben im Kapitel [Init-Container](#init-container)
> bereits vorgestellt. Dort gab es ein Beispiel mit `busybox` und `nslookup`. Hier setzen wir
> das Konzept jetzt praktisch um.

### Aufgabe

Ergänze das Deployment aus der vorherigen Übung um einen **Init-Container**, der vor dem
Start von phpMyAdmin prüft, ob MariaDB auf `localhost:3306` antwortet. Der Init-Container
verwendet das offizielle `mariadb:11`-Image und führt `mysqladmin ping` aus.

### Lösung (Schritt für Schritt)

**1. Deployment anpassen**

Füge einen `initContainers`-Block in das Deployment ein. Der Init-Container sitzt auf
derselben Ebene wie `containers` und `volumes`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: database
  namespace: k8s-training
  labels:
    app: database
spec:
  replicas: 1
  selector:
    matchLabels:
      app: database
  template:
    metadata:
      labels:
        app: database
    spec:
      initContainers:                          # ⬅️ NEU: läuft vor den App-Containern
        - name: wait-for-mariadb
          image: mariadb:11
          command:
            - sh
            - -c
            - |
              echo "Warte auf MariaDB auf localhost:3306 ..."
              until mysqladmin ping -h localhost -u root -ptrainingk8s --silent; do
                echo "MariaDB noch nicht bereit – warte 2s ..."
                sleep 2
              done
              echo "MariaDB ist bereit!"
      containers:
        - name: mariadb
          # ... bestehende Konfiguration ...
        - name: phpmyadmin
          # ... bestehende Konfiguration ...
```

**Was passiert hier?**

| Schritt | Beschreibung |
|---------|-------------|
| `image: mariadb:11` | Der Init-Container nutzt das offizielle MariaDB-Image – darin ist `mysqladmin` enthalten |
| `mysqladmin ping` | Prüft, ob der MariaDB-Server auf `localhost:3306` antwortet. Exit-Code 0 = bereit |
| `-h localhost` | MariaDB läuft im selben Pod – also über `localhost` erreichbar |
| `-u root -ptrainingk8s` | Authentifizierung mit dem Root-Passwort aus dem Secret |
| `--silent` | Nur Exit-Code, keine Ausgabe |
| `until ...; do sleep 2; done` | Wiederhole die Prüfung alle 2 Sekunden, bis MariaDB antwortet |
| `echo "MariaDB ist bereit!"` | Sobald MariaDB antwortet, beendet sich der Init-Container mit Exit-Code 0 |

**2. Deployment aktualisieren**

```bash
kubectl apply -f database-deployment.yaml
```

**3. Beobachten, was passiert**

Öffne zwei Terminals:

**Terminal 1 – Pod-Status live:**

```bash
kubectl get pods -l app=database -n k8s-training -w
```

Du siehst:

```
NAME                        READY   STATUS     RESTARTS
database-xxx                0/2     Init:0/1   0       ← Init-Container läuft
database-xxx                0/2     Init:0/1   0       ← Init-Container wartet auf MariaDB
database-xxx                0/2     Init:0/1   0       ← (wiederholt sich bis MariaDB bereit)
database-xxx                0/2     PodInitializing    ← Init-Container fertig, App-Container starten
database-xxx                1/2     Running            ← MariaDB läft, phpMyAdmin startet
database-xxx                2/2     Running            ← Beide Container laufen
```

**Terminal 2 – Logs des Init-Containers anzeigen:**

```bash
kubectl logs -l app=database -n k8s-training -c wait-for-mariadb
```

Erwartete Ausgabe:

```
Warte auf MariaDB auf localhost:3306 ...
MariaDB noch nicht bereit – warte 2s ...
MariaDB noch nicht bereit – warte 2s ...
MariaDB ist bereit!
```

**4. Test: Init-Container blockiert wirklich**

Starte den Pod neu und beobachte: Solange der Init-Container läuft, zeigt der Pod
`Init:0/1` – die App-Container (MariaDB, phpMyAdmin) starten **gar nicht erst**.

```bash
kubectl delete pod -l app=database -n k8s-training
kubectl get pods -l app=database -n k8s-training -w
```

**5. Bonus: Was passiert, wenn MariaDB nie startet?**

Ändere im Init-Container den Host von `localhost` auf einen nicht existierenden Host
(z. B. `localhost2`) und deploye erneut:

```bash
kubectl apply -f database-deployment.yaml
kubectl get pods -l app=database -n k8s-training -w
```

Der Init-Container läuft endlos – und der Pod bleibt in `Init:0/1` hängen. Die App-Container
starten nie. Kubernetes unternimmt nichts, weil Init-Container **keinen Restart** haben
(im Gegensatz zu Liveness Probes). Korrigiere den Host zurück, um den Pod freizubekommen.

### Zusammenfassung Init-Container

| Aspekt | Verhalten |
|--------|-----------|
| **Reihenfolge** | Init-Container laufen **sequenziell** vor allen App-Containern |
| **Lebensdauer** | Einmalig bis zum erfolgreichen Exit-Code 0 |
| **Bei Fehler** | Pod startet App-Container nicht – bleibt in `Init:`-Status |
| **Restart** | Init-Container werden **nicht** automatisch neu gestartet (kein CrashLoop) |
| **Typische Nutzung** | Warten auf Abhängigkeiten, Schema-Migrationen, Dateien vorbereiten |
| **Image** | Beliebiges Image – muss nicht zum App-Image passen |
